정리하면:

| 컬럼 | 값 |
|---|---|
| `department_id` | 서경대학교를 제외한 학과마다 1개 (`UNIQUE(department_id)`) |
| `role` | 전부 `BOOTH_MANAGER` |
| `password` | 평문 **`{학교명에서 공백을 뺀 앞 최대 5글자}_{region}_{학과명에서 공백을 뺀 앞 최대 5글자}`** (예: `서강대학교_SEOUL_컴퓨터공학`, `강원대학교_GANGWON_경영대학무`)을 **BCrypt cost 10**으로 해시. 5글자보다 짧으면 있는 그대로 |

### 왜 평문을 넣으면 안 되는가 (코드 확인)

- `SecurityConfig.passwordEncoder()`는 `new BCryptPasswordEncoder()`(기본 cost 10)다.
- 로그인은 `AuthServiceImpl.login` → `AuthenticationManager` → `DaoAuthenticationProvider` → `PasswordEncoder.matches(입력값, 저장값)`로 비교한다. 저장값을 BCrypt 해시(`$2a$10$` + salt + 해시, 60자)로 보고 비교하므로, **평문이 저장돼 있으면 비밀번호가 맞아도 로그인에 실패**한다.
- 기존 매니저 33명(서경대)은 전부 `$2a$10$…` 60자다.
- 회원가입 API(`AuthServiceImpl.signUp`)가 하는 일은 adminKey 확인 → 학과당 매니저 중복 확인 → `passwordEncoder.encode` → 저장뿐이다. 이벤트 등 부수효과가 없으므로 **"BCrypt 해시 + INSERT"와 결과가 같다.**

### 비밀번호 규칙의 변경 이력 — ① id → ② 전체 이름 → ③ 앞 5글자 + region → ④ 공백 제거 후 앞 5글자 + region (확정)

**① → ②** 처음 규칙 `{university_id}_{department_id}`는 환경마다 id가 같아야 성립한다. 로컬 DB를 보니 **학과 id에 빈 번호가 352개** 있다 (14,095건인데 최대 id 14,447). `innodb_autoinc_lock_mode = 2`(대량 INSERT가 id를 묶음으로 미리 잡아 두는 방식)에서 생긴 틈이라, 새로 만든 DB의 id가 같다고 보장할 수 없다. 해시를 미리 만들어 두는 옵션 B에서는 id가 어긋나면 틀린 해시가 조용히 들어간다. 이 설명 뒤 개발자가 규칙을 **이름 기반**으로 바꿨다 — 이름은 V15·V16 파일에 박혀 있어 어느 환경에서든 같다.

**② → ③** `{학교명}_{학과명}`은 192개가 BCrypt 입력 한도 72바이트를 넘었다 (아래 실측). 개발자가 앞 5글자 + region 규칙으로 바꿨다 → **최대 41바이트, 72바이트 초과 0.**

**③ → ④** 규칙 ③은 띄어쓰기도 한 글자로 세서, 5번째 글자가 공백인 학과 169개의 비밀번호가 보이지 않는 공백으로 끝났다 (예: `경영대학 무전공학과` → `경영대학␣`). "끝 공백만 제거"(가)와 "공백을 모두 뺀 뒤 5글자"(나)를 실측 비교해 개발자가 나)를 골랐다 → **공백이 들어간 비밀번호 0개.** 중복은 수용한다(ⓐ).

**BCrypt 72바이트 한도 — 이 버전의 실제 동작** (`spring-security-crypto` 7.0.4로 직접 실행):

| 호출 | 결과 |
|---|---|
| `encoder.encode(95바이트 비밀번호)` | **`IllegalArgumentException: password cannot be more than 72 bytes`** |
| `encoder.matches(95바이트 비밀번호, 앞 72바이트로 만든 해시)` | **`true`** — 비교할 때는 거부하지 않고 앞 72바이트만 쓴다 |
| 글자 경계에서 72바이트 이하로 자른 비밀번호 (70바이트) `encode` → `matches` | `true` |

BCrypt(비밀번호 해시 알고리즘)는 원래 입력의 앞 72바이트만 사용한다. 그래서 "앞 72바이트만 같으면 다른 비밀번호로도 통과되는" 성질이 있고(관련: CVE-2025-22228), 이 버전은 `encode`에서 72바이트 초과를 예외로 막는다. 반면 위 실측처럼 **`matches`는 이 입력(95바이트, 36글자)을 거부하지 않고 앞부분으로 비교해 통과**시켰다 — 한글은 글자 수는 적고 바이트 수는 많아서, 비교 시 길이 검사가 있더라도 걸리지 않을 수 있다. 이 동작은 라이브러리 버전에 따라 바뀔 수 있다.

## 결정 동인 (Decision Drivers)

1. **모든 계정이 실제로 로그인될 것** — 부하 테스트·관리자 API 검증에 쓰인다
2. **어느 환경에서든 같은 결과** — ADR-0002와 같이 Flyway로 모든 DB에 들어간다
3. **적재가 앱 기동·테스트를 느리게 하지 않을 것** — Testcontainers는 테스트마다 모든 마이그레이션을 빈 DB에 적용한다
4. **로그인 성능 측정이 현실적일 것** — 로그인 응답시간은 BCrypt 계산이 대부분이다 → cost를 낮추면 측정값이 왜곡된다 (개발자 지정: cost 10)
5. 추가 비밀값(adminKey)·실행 중인 앱에 의존하지 않을 것

## 고려한 옵션 (Considered Options)

### 옵션 A: 회원가입 API(`POST /api/auth/register`)를 14,062번 호출하는 스크립트

- 설명: 스크립트가 (universityId, departmentId, password, role, adminKey)를 만들어 가입 API를 호출한다.
- 장점: 실제 가입 경로를 그대로 탄다. 해시 생성 도구가 필요 없다
- 단점:
  - 서버가 해시를 계산하므로 순차 호출이면 약 12분 이상(HTTP 왕복 별도), 그동안 앱 3대의 CPU를 점유한다
  - adminKey(설정 비밀값)가 필요하다
  - **실행 중인 환경에만** 들어간다. V17~V19로 부스가 생기는 새 DB·Testcontainers에는 매니저가 없다 (ADR-0002와 경로가 갈린다)
  - (규칙 ②였다면 72바이트 초과 192건은 `encode`에서 예외 → 가입 실패)
- 실측 효과: 해시 52ms × 14,062 ≈ 12분 (서버 측, 추정)

### 옵션 B: BCrypt 해시를 미리 생성한 Flyway SQL (`V20`) — **개발자 선택**

- 설명: 일회성 생성 도구가 (학교명, region, 학과명)마다 비밀번호 규칙(현재 ③)으로 평문을 만들어 cost 10으로 해시해 `V20__insert_booth_managers.sql`을 만든다. 마이그레이션은 이름으로 학과를 찾아 `INSERT ... SELECT` 한다.
- 장점:
  - 적용이 SQL 한 문장이라 빠르다 (앱 기동·테스트에 해시 계산 부담 없음)
  - V17~V19와 같은 경로 → 부스가 있는 모든 DB에 매니저도 있다
  - cost 10 유지 → 로그인 성능 측정이 실제 가입 계정과 같은 조건
  - 해시를 앱과 **같은 라이브러리**(`spring-security-crypto`)로 만들어 형식 차이가 없다
- 단점:
  - 파일이 약 1.9MB로 크다 (내용 대부분이 해시)
  - 해시 생성을 한 번 돌려야 한다 (병렬 약 1분). salt가 매번 달라 다시 생성하면 파일 내용이 바뀐다 → 적용 후 파일 수정 금지(policy 4.1)라 **한 번만 생성해 커밋**한다
  - 비밀번호 규칙이 파일 밖(생성 도구)에만 있어, 규칙을 바꾸려면 새 버전 파일이 필요하다
  - (규칙 ②였다면 72바이트 초과 192건을 `encode`로 해시할 수 없었다 — 규칙 ③에서 해소)
- 실측 효과: 해시 생성 52ms/건 단일 스레드. 적용 시간은 구현 후 측정

### 옵션 C: Flyway Java 마이그레이션 (`V20__InsertBoothManagers.java`)

- 설명: 마이그레이션이 실행될 때 DB에서 학과를 읽어 그 자리에서 해시하고 배치 INSERT 한다.
- 장점: 파일이 작다. 해시 생성 도구·커밋된 해시가 없다
- 단점:
  - **모든 새 DB·모든 테스트 실행마다** 해시 14,062건을 계산한다 — cost 10이면 병렬로도 약 1분, 단일 스레드 12분. cost 10을 지키면서 쓸 수 없다 (결정 동인 3·4 충돌)
  - 적재용 코드가 운영 코드(`src/main/java`)에 들어간다 (policy 3.3)
- 실측 효과: 기동마다 해시 12분(단일)/약 1분(병렬) 추정

## 결정 (Decision)

**선택**: 옵션 B (개발자 지정 — "B안으로 ADR 작성부터해서 시작해줘. cos 10으로 해주고.")

**에이전트 의견**: 권고도 옵션 B다. 결정 동인 2·3·4를 동시에 만족하는 유일한 옵션이다. 옵션 A는 부스가 있는 새 DB에 매니저가 없게 되고, 옵션 C는 cost 10과 테스트 시간이 충돌한다.

**확정**: 옵션 B (개발자 승인 2026-09-17) — cost 10, 비밀번호 규칙 ④, 비밀번호 중복 수용. 에이전트 권고와 같다.

### 구현 규칙 (확정 시 적용)

- **생성 도구 위치**: `scripts/seed/` — AGENTS.md 3.3 "도구성 코드 위치는 최초 도입 시 확정"을 이 ADR로 확정한다. 운영 코드와 빌드(`src/`)에 포함되지 않는다
- **생성 도구**: Java 단일 파일 프로그램. 앱과 같은 `spring-security-crypto`의 `BCryptPasswordEncoder`(`$2a$`, strength 10)를 쓴다. 해시 계산은 병렬로 한다
- **입력**: 로컬 DB에서 뽑은 (학교명, region, 학과명) 목록 — 서경대학교 제외. 정렬은 V17~V19와 같은 `(학교명, region, 학과명)`
- **평문 (규칙 ④)**: `{학교명에서 공백(U+0020)을 모두 뺀 뒤 앞 최대 5글자}_{region}_{학과명에서 공백을 모두 뺀 뒤 앞 최대 5글자}`. 글자 수는 MySQL `LEFT()`와 같은 **문자(코드 포인트) 단위**로 센다. 공백 외의 문자(괄호·영문·숫자 등)는 그대로 둔다. MySQL 식으로는 `CONCAT(LEFT(REPLACE(학교명,' ',''),5),'_',region,'_',LEFT(REPLACE(학과명,' ',''),5))`와 같다. 예: `경영대학 무전공학과` → `경영대학무`, `IT 첨단자율학부` → `IT첨단자`
- **마이그레이션**: `V20__insert_booth_managers.sql`. `VALUES (학교명, region, 학과명, 해시)`를 `(학교명, region)` → `universities`, `(university_id, 학과명)` → `departments`로 `LEFT JOIN`한다. 학과를 못 찾으면 `department_id`가 NULL이 되어 `NOT NULL` 위반으로 **실패**한다 (V16 관례)
- **값**: `role = 'BOOTH_MANAGER'`, `created_at`/`modified_at = NOW(6)`
- **검증**:
  - 로컬 롤백 검증: 건수 14,062, 전부 `$2a$10$` 60자, 서경대 매니저 33 유지
  - **로그인 비교**: V20의 **14,062개 해시 전부**를, 생성 도구와 별개로 MySQL 식으로 계산한 평문과 `BCryptPasswordEncoder.matches`로 대조한다 (생성 도구의 규칙 구현 실수를 잡기 위함)
  - `./gradlew test`
  - 결과를 이슈 #14에 기록
- **평문 목록은 저장소에 남기지 않는다** — 규칙으로 누구나 다시 만들 수 있으므로 별도 파일이 필요 없다

## 결과 (Consequences)

### 개선 실측치

측정 조건: 로컬 22코어, `spring-security-crypto` 7.0.4, MySQL 8.0.46 (`festival2`, 앱 3대 기동 중, 인덱스·FK 켠 상태). 상세 LLD-0004 9.4.

| 항목 | 값 |
|---|---|
| 해시 생성 소요 (병렬 22스레드) | **63.6초** (추정 약 1분과 일치) |
| 해시 전수 검증 (`matches` 14,062건, 병렬) | 87.2초 — **실패 0** |
| V20 파일 크기 | **1,867,511바이트** (약 1.87MB, 추정 1.9MB) |
| V20 적용 소요 (트랜잭션 롤백 측정) | **0.27초** |
| Testcontainers 마이그레이션 전체 | V1~V19 4.1초 → V1~V20 **3.8초** (측정 편차 범위 — V20 추가 부담 없음) |

### 긍정적

- 전국 부스 14,062개가 모두 로그인 가능한 매니저를 갖는다 → 부스 관리자 API(주문 조회 등) 부하 테스트가 가능해진다
- 부하 테스트 스크립트가 요청에 쓰는 학교명·학과명으로 비밀번호를 바로 만들 수 있다

### 부정적 / 트레이드오프

- **비밀번호를 이름으로 짐작할 수 있다.** 학교명·학과명만 알면 어느 부스든 로그인된다. 운영 환경이 없다는 전제(ADR-0002)로 수용한다. 이 계정들은 Flyway로 모든 환경에 들어간다
- 약 1.9MB 마이그레이션 파일이 config 저장소에 추가된다
- 비밀번호가 계정마다 유일하지 않다 (규칙 ④에서 1,319개가 다른 계정과 같은 값). 로그인은 대학·학과 id로 계정을 먼저 찾고 비밀번호를 비교하므로 동작에는 영향이 없다
- 비밀번호를 원래 이름에서 바로 읽을 수 없다 (공백 제거 후 5글자) — 부하 테스트 스크립트도 같은 규칙으로 만들어야 한다
