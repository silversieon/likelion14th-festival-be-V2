## 1. 문서의 위상 — 무엇을 어디에 쓰는가

| 문서 | 성격 | 예시 |
|---|---|---|
| **AGENTS.md** | 에이전트가 **무엇을 어떤 순서로 하는가** (절차) | "이슈 → ADR → LLD → TDD → 커밋 → PR" |
| **Policy (본 문서)** | 프로젝트 전체에 지속 적용되는 **전역 방침** (무엇을 지켜야 하는가 / 왜) | "인덱스는 실측 없이 추가하지 않는다" |
| **ADR** (`docs/adr`) | 특정 시점의 **개별 결정과 근거** (옵션 비교 포함) | "주문 조회는 orders.booth_id 비정규화로 해결한다 — 옵션 비교와 실측" |
| **LLD** (`docs/lld`) | 특정 기능의 **구현 직전 상세 설계** | "이 클래스, 이 시그니처, 이 인덱스, 이 테스트" |
| **ERD** (`docs/erd`) | 현재 **DB 스키마의 사실 기록** | 테이블·컬럼·인덱스 현황 |
| **api-spec** (`docs/api-spec`) | REST API **계약** | 경로·요청·응답·에러 |

- 본 문서는 **"무엇을 지켜야 하는가(what/why)"** 를 정의한다. **"어떻게 구현하는가(how)"** 는 ADR과 LLD가 정한다.
- 본 문서에 **"ADR로 확정"** 이라 표시된 항목은 해당 기능 착수 시점에 ADR 작성이 **필수**다.
  ADR은 **고려한 옵션을 2~3개 비교**하며, 작성 후 **개발자 확인을 받기 전에는 구현 근거가 되지 않는다** (AGENTS.md ②-1).
- 본 문서에 **"⚠️ 해결 대상"** 이라 표시된 항목은 **이미 확인된 문제**다. 관련 작업을 할 때 함께 다루거나, 별도 이슈로 등록한다.

## 2. 서비스 특성과 제약 — 모든 방침의 근거

방침을 이해하려면 이 서비스가 어떤 모양인지부터 알아야 한다. 아래 특성이 이후 모든 장의 근거다.

### 2.1 트래픽 프로파일

| 특성 | 내용 | 따라오는 제약 |
|---|---|---|
| **극단적 피크성** | 1년에 며칠, 그중에서도 저녁 몇 시간에 트래픽이 몰린다. 나머지 기간은 거의 0 | 평시 성능은 의미가 없다. **피크 기준으로 설계하고 피크 기준으로 측정한다** |
| **읽기 >> 쓰기** | 부스·메뉴 조회가 압도적으로 많고, 주문 생성은 그보다 훨씬 적다 | 캐싱·읽기 최적화의 효용이 크다 (6·7장) |
| **관리자 화면은 실시간** | 부스 관리자는 주문 목록을 계속 띄워 두고 본다 | SSE 연결이 오래 유지된다. 연결 자원 관리가 중요 (11장) |
| **손님은 비로그인** | QR 오더는 인증 없이 들어온다 (`POST /api/booths/{boothId}/orders`가 `permitAll`) | 요청자 식별이 없다. 남용 방지와 자원 소유권 검증을 서버가 전부 책임진다 (13장) |
| **재시도가 잦다** | 축제장 와이파이·LTE가 불안정하다 | 멱등성이 선택이 아니라 필수 (8장) |
| **되돌릴 수 없는 실수** | 주문이 누락되면 손님이 음식을 못 받는다. 중복되면 부스가 손해를 본다 | 이벤트 유실·중복 처리 방침이 핵심 (10장) |

### 2.2 이 프로젝트가 지금 하려는 것

`AGENTS.md` 1.4의 네 갈래다. 이 문서의 3~7장이 그 방침에 해당한다.

1. **전국 단위 대학으로 확장** — 스키마 개편 (4장)
2. **대량 데이터 적재** — 수십만 → 수천만 건 (3장)
3. **대량 데이터 기준 성능 문제 해결** — 인덱스·쿼리·캐싱 (5·6장)
4. **Read Replica / CQRS 도입** — 조회 분리 (7장)

**이 프로젝트의 목적은 기능 추가가 아니라 "규모를 견디게 만드는 것"이다.** 따라서 모든 결정의 최종 심판은 **실측 수치**다 (17장).

### 2.3 아키텍처 방침 — DDD·레이어드는 적용하지 않는다

- 구조 규칙(패키지 구성, `domain`/`global` 분리, 전략 패턴 조립)은 **`AGENTS.md` 3장을 따르며 여기서 중복 정의하지 않는다.**
- 다만 그 결정의 **근거**는 여기에 남긴다: 이 프로젝트의 병목은 **도메인 복잡도가 아니라 데이터 규모**다.
  애그리거트·VO·의존성 역전을 도입해도 3-hop 조인은 빨라지지 않는다. 계층 설계에 쓸 시간을 인덱스·쿼리·Read Model에 쓴다.
- DDD 도입 여부는 성능 작업이 끝난 뒤 **별도 ADR로 재검토**한다. 지금 하지 않는다.

## 3. 대용량 데이터 처리 방침

### 3.1 규모·분포는 사용자가 정한다 (위반 금지)

- **데이터의 규모·편향·분포 조건은 항상 사용자(프롬프트)가 지정한다.** 에이전트가 임의로 가정하거나 "합리적인 값"으로 대체하지 않는다.
- LLD 9장에는 **사용자 지시 원문을 그대로 인용**한다. 요약·의역하지 않는다.
- 지시가 없으면 **묻는다.** 임의 분포로 적재한 데이터로 낸 성능 수치는 근거로 쓸 수 없다.

### 3.2 행 증폭을 항상 계산한다

주문 도메인은 한 건의 주문이 세 테이블로 번진다:

```
1 orders  →  N order_items  →  Σ(quantity) order_item_units
```

- **적재 스펙에는 세 테이블의 예상 건수를 모두 적는다.** `orders` 100만 건이 `order_item_units` 800만 건을 뜻할 수 있다.
- 이 증폭은 스토리지뿐 아니라 **조회 조인 비용과 CASCADE 삭제 비용**에도 그대로 반영된다.

### 3.3 적재 방식

- 배치 삽입(insert를 한 건씩 보내지 않고 여러 건을 묶어 한 번에 보내 왕복 횟수를 줄이는 방식) vs 저장 프로시저 선택은 **ADR로 확정**한다.
- 배치 크기·트랜잭션 단위·실패 시 재개 전략을 LLD에 명시한다. **"전부 한 트랜잭션"은 금지**한다 — 롤백 비용과 undo 로그가 감당되지 않는다.
- 적재 중 인덱스·FK를 비활성화할지는 **ADR로 확정**한다. 끄기로 했다면 **다시 켜는 절차와 검증까지** LLD에 적는다.
- **적재 스크립트는 운영 코드(`src/main`)에 두지 않는다.** 위치는 최초 도입 시 확정한다 (AGENTS.md 3.3).
- **실행 결과(적재 건수, 소요 시간, 실패 건수)를 반드시 기록한다.** 커밋 메시지 또는 이슈에 남긴다.

### 3.4 적재 대상에서 제외하는 것

- `idempotency` — 멱등성 키는 운영 중 생성되는 임시 데이터다. 더미로 채우면 만료 정리 로직 검증이 왜곡된다.
- `outbox` — 폴링 대상이므로 더미를 넣으면 발행 로직이 즉시 동작한다.
- 위 두 테이블에 부하를 주는 시나리오가 필요하면 **더미 적재가 아니라 실제 API 호출 부하**로 만든다.

## 4. 스키마·마이그레이션 방침

### 4.1 Flyway가 유일한 스키마 변경 경로

- 스키마 변경은 **항상 새 마이그레이션 파일 추가**로만 한다: `V{N+1}__<snake_case_설명>.sql`
- **이미 적용된 마이그레이션 파일은 절대 수정하지 않는다.** 체크섬이 달라지면 애플리케이션이 기동하지 않는다.
- JPA `ddl-auto`가 스키마를 만들게 하지 않는다. 엔티티와 DDL이 어긋나면 **DDL이 사실이고 엔티티가 틀린 것**이다.
- **마이그레이션과 `docs/erd/`는 같은 PR에서 함께 바뀐다.** 둘이 어긋난 상태로 머지하지 않는다.

### 4.2 스키마 컨벤션

현행 관례는 `docs/erd/erd-0001-initial-schema.md` 2장에 정리되어 있다. 신규 테이블·컬럼은 그것을 따른다. 핵심만 옮기면:

- PK는 `BIGINT AUTO_INCREMENT`, 물리 FK를 적극 사용, enum은 `VARCHAR` + `@Enumerated(STRING)`
- 금액은 `INT`(KRW), 불리언은 `TINYINT(1) NOT NULL DEFAULT 0`
- 시각은 `DATETIME(6)`, `BaseTimeEntity` 상속으로 자동 관리
- **신규 테이블 이름은 복수형 `snake_case`** (기존의 단수/복수 혼용은 유지)

### 4.3 파괴적 변경(destructive change) 규칙

컬럼 삭제, 타입 축소, NOT NULL 추가, UNIQUE 추가는 **기존 데이터를 깨뜨릴 수 있다.**

- 반드시 **ADR**로 결정하고, LLD 7.2에 **백필(backfill) 계획과 롤백 방법**을 적는다.
- 큰 테이블의 `ALTER TABLE`은 잠금 시간이 길다. 적재 후 테이블 크기를 고려해 실행 시점(축제 기간 외)을 정한다.
- **다단계로 나눈다**: ① 컬럼 추가(nullable) → ② 백필 → ③ 애플리케이션이 새 컬럼 사용 → ④ NOT NULL/제약 추가 → ⑤ 옛 컬럼 제거.
  한 마이그레이션에 다 넣지 않는다.

### 4.4 전국 확장 시 반드시 다룰 것 (⚠️ 해결 대상)

`AGENTS.md` 1.4-①의 본체이며, ERD 6.1과 짝을 이룬다.

| 항목 | 문제 |
|---|---|
| `booth.department` UNIQUE | 대학이 여러 개가 되면 **같은 학과명이 중복**되어 제약이 깨진다 |
| `Department` Java enum | 서경대 학과 30여 개가 코드에 하드코딩되어 있다. **전국 규모를 enum으로 감당할 수 없다** |
| JWT subject = Department 이름 | 위 enum이 바뀌면 **인증 흐름 전체가 영향**을 받는다 |
| `managers.department` ↔ `booth.department` | FK 없이 **문자열 값으로만** 이어져 있다. 대학이 늘면 동명 학과에서 소유권 판정이 깨진다 |

→ 위 넷은 **한 덩어리로 묶어 하나의 ADR**로 결정한다. 따로 고치면 중간 상태가 깨진다.

## 5. 조회 성능·인덱싱 방침

### 5.1 실측 없는 최적화 금지 (핵심 원칙)

- **`EXPLAIN` 실행 계획과 응답시간 측정 없이 인덱스를 추가하지 않는다.** 추측 기반 인덱스는 쓰기를 느리게 만들 뿐이다.
- 개선 작업은 항상 이 순서다:
  **① 부하 재현 → ② 느린 쿼리 특정 → ③ `EXPLAIN`으로 원인 확인 → ④ 대안 적용 → ⑤ 같은 조건에서 재측정 → ⑥ ADR에 Before/After 기록**
- ⑥ 없이 병합된 성능 개선은 **되돌릴 근거도 없다.** 반드시 남긴다.

### 5.2 현재 상태 — 조회 인덱스가 없다 (⚠️ 해결 대상)

`docs/erd/erd-0001-initial-schema.md` 5장 참조. **명시적으로 설계한 보조 인덱스가 하나도 없다.**
PK, UNIQUE 제약, MySQL이 FK 때문에 자동 생성한 인덱스가 전부다.

지금 인덱스 없이 도는 대표 쿼리:

| 대상 | 문제 |
|---|---|
| `orders` 상태별 목록 | `order_status` 인덱스 없음 |
| `orders` 커서 정렬·일자 필터 | `created_at`, `completed_at`, `canceled_at` 인덱스 없음 |
| `orders` keyword 검색 | `customer_name`, `customer_phone_number` 인덱스 없음 (LIKE 검색이면 인덱스로도 한계) |
| `outbox` 폴링 | `published_at` 인덱스 없음인데 **200ms마다** 스캔한다 |

### 5.3 주문의 부스 소속 판별 — 가장 큰 구조적 병목 (⚠️ 해결 대상)

**`orders` 테이블에 `booth_id`가 없다.** 주문이 어느 부스 것인지는 이 경로로만 알 수 있다:

```
orders → order_items → booth_menu → booth.department
```

부스 관리자의 모든 주문 조회(대기/조리/완료/취소)와 매출 집계가 이 3-hop 조인을 탄다.
대량 데이터에서 **가장 먼저 무너지는 지점**이며, 다음 두 방향이 후보다 — **ADR로 확정**한다:

1. **비정규화**: `orders.booth_id` 컬럼 추가 + 백필 (4.3의 다단계 절차 필요)
2. **Read Model**: 조회 전용 비정규화 저장소로 분리 (7장)

### 5.4 인덱스 설계 규칙

- **복합 인덱스는 컬럼 순서가 전부다.** 등호(`=`) 조건 컬럼을 앞에, 범위·정렬 컬럼을 뒤에 둔다.
  예: `WHERE order_status = ? ORDER BY created_at DESC` → `(order_status, created_at)`
- 커버링 인덱스(조회에 필요한 컬럼을 모두 인덱스에 포함시켜, 실제 테이블을 다시 읽지 않고 인덱스만으로 조회를 끝내는 방식)를 쓸 때는 **포함 컬럼과 그 근거를 LLD에 적는다.** 무한정 넓히면 인덱스가 테이블만큼 커진다.
- **인덱스를 추가하면 쓰기가 느려진다.** LLD에 "이 인덱스로 느려지는 쓰기 경로"를 함께 적는다. 주문 생성(피크 시 가장 중요한 쓰기)에 영향이 가는지 반드시 확인한다.
- 카디널리티(값의 다양성)가 낮은 컬럼 단독 인덱스는 효과가 없다. `order_status`(4개 값) 단독 인덱스가 대표적 — 반드시 정렬 키와 복합으로 만든다.

### 5.5 페이지네이션은 커서 방식을 유지한다

- 목록 조회는 **커서 페이지네이션**(마지막으로 읽은 위치를 커서로 들고 다니며 다음 페이지를 읽는 방식)을 쓴다. `OFFSET` 방식은 뒤로 갈수록 앞 행을 전부 세어야 해서 대량 데이터에서 급격히 느려진다.
- **커서의 정렬 키 조합과 인덱스는 반드시 일치해야 한다.** 정렬 키가 인덱스로 커버되지 않으면 `filesort`가 발생해 커서를 쓰는 의미가 사라진다.
- 커서는 클라이언트에게 **불투명한 문자열**이다. 내부 구조를 계약으로 노출하지 않는다 (api-conventions 4.1).
- **정렬 키에 유일성이 없으면 tie-breaker로 PK를 덧붙인다.** 같은 `created_at`이 여러 건이면 페이지 경계에서 행이 누락되거나 중복된다.

### 5.6 N+1과 지연 로딩

- 목록 조회에서 연관 엔티티를 순회하면 **N+1 쿼리**(1건 조회 후 연관 데이터를 건별로 또 조회하는 문제)가 난다. 주문 목록은 `order_items`, `order_item_units`를 함께 보여주므로 특히 위험하다.
- 조회 API는 **엔티티 그래프를 순회하는 대신 DTO 프로젝션 또는 `JOIN FETCH`** 를 쓴다.
- **`JOIN FETCH` + 페이지네이션 조합에 주의한다.** 컬렉션을 fetch join 하면서 페이징하면 Hibernate가 전 행을 메모리로 올린다(`HHH90003004` 경고). 컬렉션은 별도 조회로 나눈다.
- 조회 트랜잭션은 `@Transactional(readOnly = true)`로 선언한다.

## 6. 캐싱 방침 (Redis)

### 6.1 캐싱 전에 먼저 할 것

**캐싱은 느린 쿼리의 해결책이 아니라 마지막 수단이다.** 순서를 지킨다:

1. 쿼리·인덱스로 해결 가능한가? → 그것부터 한다 (5장)
2. 그래도 느린가 / 호출 빈도가 압도적인가? → 캐싱을 검토한다
3. 캐싱이 정합성을 깨는가? → 깨져도 되는 범위인지 판단한다

캐시로 덮으면 **원래 쿼리가 느리다는 사실이 감춰진다.** 실측치는 캐시 미스 기준으로도 남긴다.

### 6.2 캐싱 대상 판단 기준

| 캐싱하기 좋은 것 | 캐싱하면 안 되는 것 |
|---|---|
| 부스 목록·상세, 메뉴 목록 (읽기 압도적, 변경 드묾) | **주문 목록** — 관리자가 실시간으로 봐야 한다 |
| 번역 결과 (이미 `booth_menu_dictionary`가 같은 역할) | 매출 집계 — 실시간 정확도 요구 |
| 부스 운영 시간 | 멱등성 응답 이외의 쓰기 결과 |

### 6.3 캐시 설계 규칙 (도입 시 ADR 필수)

- **키·TTL·무효화 시점 세 가지를 반드시 함께 정의한다.** 셋 중 하나라도 비면 캐시를 넣지 않는다.
- 키에는 **응답을 가르는 모든 파라미터**를 넣는다. 언어(`lang`), 위치(`location`) 같은 필터를 빠뜨리면 다른 사용자에게 남의 응답이 나간다.
- **무효화는 "쓰기 시점에 삭제(evict)"를 기본**으로 한다. TTL 만료만 믿는 캐시는 부스 관리자가 메뉴 품절 처리를 해도 손님 화면이 안 바뀌는 사고를 낸다.
- **캐시 장애가 서비스 장애가 되면 안 된다.** Redis가 죽으면 DB로 폴백한다 (이미 `FallbackIdempotencyStrategy`가 같은 원칙을 구현하고 있다 — 8.3).
- 피크 시작 시점의 **캐시 스탬피드**(캐시가 비어 있는 순간 동시 요청이 전부 DB로 몰리는 현상)를 고려한다. 사전 워밍업 또는 단일 갱신 락을 검토한다.

### 6.4 Redis는 이미 세 가지 역할을 한다

새 용도를 추가할 때 **기존 용도와 키 네임스페이스가 겹치지 않게** 한다.

| 용도 | 위치 |
|---|---|
| Refresh Token 저장 | `global/infra/redis/RefreshTokenRepository` |
| 멱등성 키·응답 캐시 | `global/util/idempotency/strategy/redis` |
| SSE 이벤트 전달 (Pub/Sub 또는 Streams) | `domain/order/sse/redis` |

## 7. CQRS / Read Replica / Read Model 방침

### 7.1 도입 순서 (건너뛰지 않는다)

성능 문제는 **싼 해법부터** 쓴다. 아래 순서를 지키고, 각 단계에서 "이걸로 부족하다"는 실측을 남긴 뒤 다음으로 넘어간다.

```
① 인덱스·쿼리 튜닝  →  ② 캐싱  →  ③ Read Replica  →  ④ CQRS + Read Model(MongoDB)
   (5장)               (6장)      (읽기 부하 분산)      (조회 모델 자체를 분리)
```

- ③, ④는 각각 **ADR 필수**다. ①·②로 해결되는 문제에 ④를 쓰면 정합성 복잡도만 떠안는다.

### 7.2 Read Replica 도입 시

- **어떤 API가 Replica를 읽는지 LLD에 목록으로 명시한다.** "조회니까 전부"는 금지 — 복제 지연을 못 견디는 조회가 있다.
- **복제 지연(replication lag)** 을 전제로 설계한다. 쓰기 직후 자신의 결과를 읽는 흐름(예: 주문 생성 후 목록 갱신)은 **Primary를 읽거나 응답 데이터를 그대로 쓴다.**
- 라우팅 방식(`@Transactional(readOnly=true)` 기반 자동 분기 등)은 ADR로 확정한다.

### 7.3 CQRS / Read Model 도입 시

- 조회 전용 로직은 `domain/<도메인>/query/`로 분리한다 (AGENTS.md 3.2).
- **Read Model 갱신 트리거로 기존 아웃박스(`global/outbox`)를 재사용할 수 있는지 반드시 옵션에 넣는다.** 주문 상태 전이가 이미 전부 outbox에 적재되고 있다. 새 파이프라인을 만들기 전에 이것부터 검토한다.
- **정합성 수준을 수치로 못 박는다.** "최종적 일관성"이라고만 쓰지 말고 **"주문 생성 후 N초 이내 반영"** 처럼 허용 지연을 적는다. 부스 관리자 화면은 이 지연을 사람이 체감한다.
- Read Model이 깨졌을 때 **원본(MySQL)에서 재생성하는 절차**를 함께 설계한다. 재생성할 수 없는 Read Model은 도입하지 않는다.

## 8. 멱등성 방침

### 8.1 원칙

- **주문 생성은 반드시 멱등해야 한다.** 축제장 네트워크는 불안정하고, 손님은 응답이 없으면 다시 누른다. **주문이 두 번 들어가면 부스가 손해를 본다.**
- 중복 판정의 최종 방어선은 애플리케이션 검사(SELECT)가 아니라 **DB PK/UNIQUE 제약**이다. 검사와 삽입 사이의 경합은 제약 위반 예외로 잡아 중복 흐름으로 넘긴다.

### 8.2 구현 방침

- 클라이언트는 `Idempotency-Key` 헤더(UUID)를 필수로 보낸다. 누락 시 400.
- 서버는 키를 `PROCESSING`으로 선점한 뒤 처리하고, 완료 시 **응답 스냅샷을 저장**한다. 재요청에는 그 스냅샷을 그대로 돌려주고 **재처리하지 않는다.**
- 처리 규칙과 응답은 `docs/api-spec/api-conventions.md` 7장이 계약이다. 여기서 중복 정의하지 않는다.
- **멱등성 처리는 트랜잭션 바깥에서 일어나야 한다.** 현재 `@Idempotent` AOP(`@Order(0)`)가 `@Transactional`이 붙은 `OrderProcessor.processOrder`보다 바깥에서 돈다. 이 순서를 깨지 않는다 — 트랜잭션 안에서 키를 잡으면 롤백 시 키까지 사라져 중복 방어가 무력해진다.

### 8.3 전략 선택 (4종)

`IdempotencyType`: `DB` / `REDIS` / `WRITETHROUGH` / `FALLBACK`

| 전략 | 동작 | 쓰는 곳 |
|---|---|---|
| `DB` | MySQL `idempotency` 테이블만 사용 | Redis 없이 동작해야 하는 경우 |
| `REDIS` | Redis만 사용 (빠르지만 휘발) | 유실 허용 가능한 경우 |
| `WRITETHROUGH` | Redis 선점 → DB 선점 → 처리 → 양쪽에 응답 저장 | 속도와 내구성 동시 확보 |
| **`FALLBACK`** | `WRITETHROUGH`를 **서킷브레이커 + 재시도**로 감싸고, Redis 실패 시 **DB로 폴백** | **주문 생성 (현재 기본값)** |

- **새 API에 멱등성을 붙일 때는 어떤 전략을 왜 골랐는지 LLD에 남긴다.** 기본값 복붙 금지.
- `FALLBACK`은 Redis 장애가 주문 실패로 번지지 않게 하는 구조다. **이 원칙(캐시 장애 ≠ 서비스 장애)을 다른 Redis 사용처에도 적용한다** (6.3).

### 8.4 키 보관 기간 (⚠️ 해결 대상)

현재 `DbIdempotencyScheduler`는 **매일 새벽 1시**에 **"10분보다 오래된"** 키를 삭제한다.

- 두 값이 어긋나 있다: 정리 주기는 하루인데 만료 기준은 10분이다. 결과적으로 **키는 최대 약 24시간 남아 있고**, 재요청이 멱등하게 처리되는 창이 실행 시각에 따라 들쭉날쭉하다.
- **"멱등성 키를 얼마나 오래 보관할 것인가"를 하나의 값으로 정의하고, 정리 주기를 그에 맞춰야 한다.** 보관 기간은 **ADR로 확정**한다.
- 판단 기준: 손님이 재시도할 수 있는 현실적인 시간(수 분) + 축제 운영 시간 + 테이블 증가 속도.

### 8.5 검증

- 멱등성은 단위 테스트로 증명되지 않는다. **동시 요청 통합 테스트**(`ExecutorService` + `CountDownLatch`로 같은 키 N건 동시 요청 → 주문 1건만 생성됨을 검증)를 LLD 13.2에 반드시 넣는다.
- 통합 테스트 DB는 실제 제약 동작이 같은 **MySQL(Testcontainers)** 를 쓴다. 인메모리 DB는 제약 의미가 달라 검증이 무효다.

## 9. 동시성·정합성 방침

### 9.1 이 서비스의 동시성은 "잔액"이 아니라 "상태 전이"다

돈을 직접 옮기지 않으므로 계좌형 락 전략이 필요 없다. 대신 아래가 경합 지점이다.

| 경합 지점 | 현재 방어 |
|---|---|
| 같은 주문의 상태를 두 관리자가 동시에 변경 | `Order.changeOrderStatus`의 전이 규칙(`OrderStatus.canChangeTo`)이 **엔티티 안에서** 검증 |
| 같은 멱등성 키로 동시 주문 생성 | `idempotency` PK 제약 (8장) |
| 아웃박스 이벤트를 여러 인스턴스가 동시 폴링 | `FOR UPDATE SKIP LOCKED` (10.3) |
| 품절 메뉴 동시 주문 | **방어 없음** (9.3) |

### 9.2 상태 전이는 엔티티가 강제한다

- 상태 변경은 반드시 **의도가 드러나는 엔티티 메서드**로만 한다 (`changeOrderStatus`, `cancelOrder`, `changeStatus`). **setter 금지.**
- 전이 가능 여부(`OrderStatus.canChangeTo`), 지난 날짜 주문 되돌리기 금지 같은 규칙은 **서비스가 아니라 엔티티 안에** 둔다. 서비스에 흩어지면 호출 경로마다 검증이 빠진다.
- 전이 규칙을 바꾸면 **SSE 이벤트 흐름도 함께 바뀐다** (11장). 짝으로 검토한다.

### 9.3 품절·시간대 검증은 원자적이지 않다 (⚠️ 인지하고 수용)

`OrderValidator`는 주문 시점에 메뉴의 품절 여부와 시간대를 **읽어서 검사**할 뿐, 잠그지 않는다.

- 따라서 **품절 처리와 주문이 동시에 일어나면 품절 메뉴 주문이 통과할 수 있다.**
- **현재는 이를 수용한다.** 재고 수량 개념이 없고(품절은 관리자가 수동 토글), 부스가 현장에서 대응 가능하기 때문이다.
- **재고 수량을 도입하는 순간 이 방침은 무효가 된다.** 그때는 락 전략을 **ADR로 확정**해야 한다.

### 9.4 트랜잭션 규칙

- `@Transactional`은 **서비스/프로세서 계층에만** 선언한다. 컨트롤러·리포지토리에 선언하지 않는다.
- 조회는 `readOnly = true`.
- **트랜잭션은 짧게 유지한다.** 트랜잭션 안에서 금지: 외부 API 호출(S3, AI 번역), 파일 I/O, `Thread.sleep`, SSE 전송.
  트랜잭션은 DB 커넥션을 점유한다. 그 안에서 느린 외부 호출을 하면 **커넥션 풀이 고갈되어 서비스 전체가 멈춘다.**
- 커넥션 풀 크기를 늘리는 것은 경합의 해법이 아니다. **DB 쪽 대기만 늘어난다.**

## 10. 이벤트 발행·전달 방침

### 10.1 두 가지 발행 방식이 공존한다

`order.event.pattern` 설정으로 전환한다.

| 방식 | 리스너 | 발행 시점 | 유실 가능성 |
|---|---|---|---|
| `direct` (기본) | `OrderDirectEventListener` | `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` | **있음** — 커밋 후 애플리케이션이 죽으면 이벤트가 사라진다 |
| `outbox` | `OrderOutboxEventListener` | `@EventListener` — **비즈니스 트랜잭션과 같은 트랜잭션**에서 `outbox` INSERT | **없음** — 커밋된 이벤트는 반드시 발행된다 |

### 10.2 리스너 애노테이션 규칙 (위반 금지)

이 두 줄을 바꾸면 정합성이 깨진다. 이유를 알고 유지한다.

- **`direct` 리스너는 반드시 `@TransactionalEventListener(AFTER_COMMIT)`** 를 쓴다.
  평범한 `@EventListener`로 바꾸면 **롤백된 주문에 대해서도 SSE 알림이 나간다** — 부스 화면에 존재하지 않는 주문이 뜬다.
- **`outbox` 리스너는 반드시 평범한 `@EventListener`** 를 쓴다.
  `AFTER_COMMIT`으로 바꾸면 **아웃박스 INSERT가 비즈니스 트랜잭션 밖으로 나가** 아웃박스 패턴 자체가 무의미해진다(주문은 커밋됐는데 이벤트 행이 없는 상태가 가능해진다).

### 10.3 아웃박스 폴링

`PollingPublisher`가 `@Scheduled(fixedDelay = 200)`으로 미발행 행을 읽어 발행한다.

```sql
SELECT * FROM outbox WHERE published_at IS NULL ORDER BY id ASC LIMIT :limit FOR UPDATE SKIP LOCKED
```

- **`FOR UPDATE SKIP LOCKED`**(다른 트랜잭션이 잠근 행은 건너뛰고 잠기지 않은 행만 잠그는 방식)로 다중 인스턴스 중복 발행을 막는다. 이 절을 제거하지 않는다.
- ⚠️ **해결 대상 1 — 처리량**: 현재 `findPendingEvents(1)`로 **한 번에 1건**만 가져온다. 200ms 주기와 곱하면 **초당 최대 5건**이다. 피크 주문량이 이를 넘으면 SSE 알림이 지연 누적된다. 배치 크기와 주기는 실측 후 조정한다.
- ⚠️ **해결 대상 2 — 인덱스**: `published_at`에 인덱스가 없다. 발행 완료 행이 쌓일수록 스캔 범위가 커진다 (5.2).
- ⚠️ **해결 대상 3 — 보관 정책**: 발행된 행을 지우지 않아 `outbox`가 **무한 증가**한다. TTL 삭제 배치 또는 파티셔닝을 결정한다.

### 10.4 전달 보장 수준 — at-least-once

**아웃박스도 Redis Streams도 "최소 1회" 전달이다. 중복이 올 수 있다.**

- `OrderStreamListener`는 처리 성공 후에만 `ACK`한다. 처리 도중 죽으면 미ACK 상태로 남아 **재전달된다.**
- 따라서 **이벤트 소비 측(SSE 전송, 향후 Read Model 갱신)은 중복 수신에 안전해야 한다.**
  - SSE 알림 중복은 화면 깜빡임 정도라 현재 수용한다.
  - **Read Model 갱신을 붙일 때는 다르다.** 같은 이벤트를 두 번 반영해도 결과가 같도록(멱등하게) 설계해야 한다 — 7.3에서 반드시 다룬다.
- 이벤트 페이로드에 **순서 판정 근거**(주문 id + 상태, 또는 outbox id)를 포함시켜, 늦게 도착한 옛 이벤트가 최신 상태를 덮어쓰지 않게 한다.

### 10.5 이벤트 이름은 계약이다

- SSE 이벤트 이름(`OrderSseEventType`)은 **프런트엔드가 문자열로 구독**한다. 오타 하나가 곧 장애다.
- 이벤트를 추가·변경·삭제하면 `docs/api-spec/order-sse.md`와 코드를 **같은 PR에서** 고친다.
- 아웃박스 `event_type` 컬럼에도 같은 문자열이 저장된다. 이름을 바꾸면 **이미 적재된 미발행 행이 역직렬화에 실패한다.** 이름 변경은 사실상 파괴적 변경이다 — 4.3 절차를 따른다.

## 11. 실시간 알림(SSE) 방침

### 11.1 세 가지 전달 방식

`sse.strategy` / `sse.redis.mode`로 전환한다. **클라이언트 계약에는 영향이 없다** — 서버 내부 구현이다.

| 설정 | 동작 | 한계 |
|---|---|---|
| `local` | 인스턴스 내부 `ConcurrentHashMap`에 Emitter 보관 | **단일 인스턴스에서만 동작.** 스케일 아웃하면 다른 인스턴스의 구독자에게 알림이 안 간다 |
| `distributed` + `pubsub` | Redis Pub/Sub로 인스턴스 간 전파 | Pub/Sub는 **구독자가 없는 순간의 메시지를 버린다** — 재연결 틈에 유실 |
| `distributed` + `stream` | Redis Streams + 소비자 그룹 + ACK | 유실 방지. **중복 전달은 있다** (10.4) |

- **다중 인스턴스로 운영한다면 `local`을 쓰지 않는다.** 이것이 Streams를 도입한 이유다.

### 11.2 연결 자원 관리

부스 관리자는 화면을 켜 두므로 **SSE 연결이 몇 시간씩 유지된다.**

- Emitter는 반드시 **`onCompletion` / `onTimeout` / `onError`에서 레지스트리에서 제거**한다. 제거를 빠뜨리면 죽은 Emitter가 쌓여 메모리를 잠식하고, 전송할 때마다 예외가 난다.
- **`AsyncRequestNotUsableException` / `AsyncRequestTimeoutException`은 정상 흐름이다.** 클라이언트가 탭을 닫으면 발생한다. `GlobalExceptionHandler`가 본문 없이 로그만 남기는 이유이며, 이 처리를 에러 응답으로 바꾸지 않는다.
- SSE 전송은 **트랜잭션 밖에서** 한다 (9.4).

### 11.3 구독자 조회 성능 (⚠️ 해결 대상)

`LocalOrderSseEmitterStore`는 `Map<"{boothId}:{type}", List<SseEmitter>>` 구조다.

- `findByBoothIdAndSubscribeType`은 키 직접 조회라 빠르다.
- **`findByBoothId`는 전체 엔트리를 스트림으로 훑으며 `startsWith`로 필터한다.** 부스 수(= 키 개수)에 비례해 느려진다.
  **전국 확장으로 부스가 수천 개가 되면 이 메서드가 병목이 된다.** 자료구조를 2단 맵(`boothId → type → List`)으로 바꾸는 것이 후보다.

### 11.4 SSE 페이로드 규칙

- SSE 이벤트의 `data`는 **`BaseResponse`로 감싸지 않는다.** envelope은 HTTP 응답 규약이다 (api-conventions 8장).
- 페이로드에 **부스·주문 식별자를 항상 포함**시킨다. 클라이언트가 어느 항목을 갱신할지 판단할 수 있어야 한다.
- 페이로드를 키우지 않는다. SSE는 다수 연결에 브로드캐스트되므로 크기가 곧 대역폭이다. **목록 전체가 아니라 변경분만** 보낸다.

## 12. 비동기·스케줄러 방침

### 12.1 이벤트 비동기 실행 풀 (⚠️ 해결 대상)

`AsyncConfig.eventExecutor`: **core 2 / max 4 / queue 20 / prefix `event-async-`**

- ⚠️ **큐가 20이다.** 피크에 주문이 몰리면 큐가 차고, 그 뒤 작업은 기본 거부 정책(`AbortPolicy`)에 따라 **`RejectedExecutionException`으로 버려진다** — 즉 **SSE 알림이 조용히 유실된다.**
  풀 크기·큐 용량·거부 정책(`CallerRunsPolicy` 등)은 **피크 부하 실측 후 조정**하고 근거를 ADR에 남긴다.
- ⚠️ **MDC가 전파되지 않는다.** `TaskDecorator`가 없어 `@Async` 스레드로 넘어가는 순간 `traceId`가 사라진다. 주문 생성과 그 SSE 알림 로그를 **하나의 요청으로 이어서 추적할 수 없다** (15.2).

### 12.2 스케줄러 — 다중 인스턴스에서 중복 실행된다 (⚠️ 해결 대상)

현재 세 개의 스케줄러가 돈다.

| 스케줄러 | 주기 | 다중 인스턴스 안전성 |
|---|---|---|
| `PollingPublisher` | 200ms | ✅ 안전 — `FOR UPDATE SKIP LOCKED` |
| `BoothScheduler.updateBoothStatusEveryMinute` | 매분 | ❌ **모든 인스턴스가 동시에 전체 부스를 UPDATE** |
| `BoothScheduler.dailyBoothStatusToClose` | 매일 01:00 | ❌ 중복 실행 |
| `DbIdempotencyScheduler` | 매일 01:00 | ❌ 중복 실행 (삭제라 결과는 같지만 부하는 N배) |

- **스케줄 작업은 "여러 인스턴스에서 동시에 돌아도 안전한가"를 반드시 따진다.** 안전하지 않으면 분산 락(Redis) 또는 리더 선출이 필요하다 — **도입 시 ADR**.
- ⚠️ **전국 확장 시 `updateBoothStatusEveryMinute`는 재설계 대상이다.** 부스가 수천~수만 개가 되면 **매분 전체 부스를 훑는 UPDATE**가 감당되지 않는다. 대상을 좁히거나(변경이 필요한 부스만), 상태를 저장하지 않고 조회 시점에 계산하는 방향을 검토한다.
- 새 스케줄 작업을 추가할 때는 **주기·대상 건수·최악의 실행 시간**을 LLD에 적는다. 주기보다 실행이 오래 걸리면 작업이 겹친다.

## 13. 인증·인가·자원 소유권 방침

### 13.1 현재 구조

- JWT 직접 구현. Access Token은 `Authorization: Bearer` **또는 `ACCESS_TOKEN` 쿠키**, Refresh Token은 `REFRESH_TOKEN` 쿠키로만 받는다.
- Refresh Token은 DB가 아니라 **Redis**에 보관한다.
- 비밀번호는 **BCrypt** 해시로 저장한다. 평문·복호화 가능 저장 금지.
- **JWT의 subject는 `Department` enum 이름**이며, 컨트롤러는 `@AuthenticationPrincipal String departmentName`으로 받는다.
- 인가는 `@PreAuthorize`로 **메서드에 건다.** 서비스 내부에서 역할을 if로 검사하지 않는다.

### 13.2 자원 소유권은 서버가 검증한다 (⚠️ 해결 대상)

**"어느 부스의 데이터인가"를 경로가 아니라 토큰이 결정하는 API가 많다.** 이 구조 자체는 유지하되, 아래 규칙을 지킨다.

- **경로 변수로 받은 식별자가 요청자 소유인지 반드시 검증한다.** 검증 없이 `findById`만 하면 남의 부스 데이터를 조작할 수 있다.
- ⚠️ **확인된 누락**: 주문 생성(`OrderProcessor.processOrder`)은 `boothMenuIds`를 `findAllById`로 조회하고 **개수만 대조**한다. 그 메뉴들이 **`boothId`에 속한 메뉴인지 검증하지 않는다.**
  즉 A 부스 엔드포인트로 B 부스의 메뉴를 주문할 수 있다. 이 경로는 **비로그인(`permitAll`)** 이라 더 위험하다.
  → 조회 시점에 `booth_id` 조건을 함께 걸거나, 조회 후 소속을 검증하도록 고쳐야 한다.
- 인증 실패·토큰 오류 응답 메시지는 **계정 존재 여부가 유추되지 않도록** 통일한다.

### 13.3 비로그인 엔드포인트 (QR 오더)

`POST /api/booths/{boothId}/orders`는 `permitAll`이다. 요청자를 식별할 수 없으므로:

- **입력 검증을 서버가 전부 책임진다.** 가격·시간대·품절·부스 상태 검증을 클라이언트에 위임하지 않는다 (현재 `OrderValidator`가 담당).
- **가격은 반드시 서버의 값과 대조한다.** 클라이언트가 보낸 `menuPrice`를 그대로 믿지 않는다 (`ORDER_MENU_PRICE_MISMATCH`).
- 남용(장난 주문 폭주) 방어 수단이 현재 없다. **필요해지면 IP·부스 단위 레이트 리밋을 ADR로 결정**한다.

### 13.4 민감정보

- 비밀번호·토큰은 **어떤 로그에도 남기지 않는다.**
- 주문자 이름·전화번호는 개인정보다. **로그에 전화번호 원문을 남기지 않는다.** 필요하면 마스킹한다.
  (현재 주문 생성 로그는 주문자명을 남긴다 — 보관 기준을 정할 때 함께 검토한다.)

## 14. 응답·예외 방침

### 14.1 계약은 api-conventions가 단일 기준

응답 envelope(`BaseResponse`), 에러 코드 체계, 상태 코드 매핑, 헤더 규약의 **상세는 `docs/api-spec/api-conventions.md`가 정의한다.** 여기서 중복 정의하지 않는다.

이 문서가 정하는 것은 **원칙**뿐이다:

- **모든 REST 응답은 성공·실패를 가리지 않고 공통 envelope으로 감싼다.** 클라이언트 파싱이 한 갈래로 유지되어야 한다.
- **HTTP 상태 코드를 살려 둔다.** envelope은 상태 코드를 대체하지 않고 덧붙인다. `200 OK` + `success: false` 조합은 존재하지 않는다.
- **실패는 예외를 던지는 것으로 끝낸다.** 컨트롤러는 try-catch 하지 않고, `@RestControllerAdvice`가 변환한다. 도메인·서비스는 HTTP를 모른다.
- **5xx 메시지에 내부 구조를 노출하지 않는다.** 상세는 로그에만 남긴다.

### 14.2 에러 코드가 응답에 나가지 않는다 (⚠️ 해결 대상)

`BaseResponse.error(int, String)`는 HTTP 상태값과 메시지만 담는다. `ORDER_4001` 같은 코드는 **로그에만 남는다.**

- 결과적으로 **클라이언트는 message 문자열로만 상황을 구분할 수 있다.** 따라서 **기존 message를 바꾸는 것은 계약 변경**이다. 프런트 합의 없이 고치지 않는다.
- 이 구조를 바꾸는 것(`errorCode` 필드 추가)은 **프런트 계약이 깨지는 변경**이므로 **ADR 필수**다.
- 함께 정리할 것: `OrderErrorCode`의 **`ORDER_4007` 중복**, `ORDER_4001`/`ORDER4031` 포맷 혼용 (api-conventions 5.3).

### 14.3 예외 래핑 주의

`IdempotencyAspect`는 `joinPoint.proceed()`의 `Throwable`을 `RuntimeException`으로 감싼다.
Spring의 예외 핸들러가 원인(cause)을 따라 올라가 주기 때문에 **현재는 `CustomException`이 정상적으로 매핑된다.**

- 다만 이는 **프레임워크 동작에 기댄 것**이다. AOP를 추가하거나 예외 처리 경로를 바꿀 때 이 의존을 인지한다.
- 새로 AOP를 만든다면 **도메인 예외는 감싸지 말고 그대로 통과시킨다.**

## 15. 로깅·관측 방침

### 15.1 로그에 남길 것

- **주문 생성·상태 전이는 반드시 로그로 남긴다**: 주문 식별자, 부스(학과), 결과. 축제 당일 분쟁의 유일한 근거다.
- 검증 실패(`OrderValidator`)는 `WARN`으로 남기고, **무엇이 왜 틀렸는지**(요청 값 vs 실제 값)를 함께 적는다.
- 예상치 못한 예외는 `ERROR` + 스택트레이스. **예상된 비즈니스 실패에 스택트레이스를 찍지 않는다** — 축제 당일 로그가 묻힌다.
- **개인정보(전화번호)와 자격증명(토큰·비밀번호)은 남기지 않는다** (13.4).

### 15.2 추적성 — traceId (⚠️ 해결 대상)

`MdcFilter`가 요청마다 8자리 `traceId`와 `clientIp`를 MDC에 넣는다.

- ⚠️ **스레드 경계를 넘으면 유실된다.** `@Async("eventExecutor")`, `@Scheduled`, SSE 전송 스레드로 넘어가는 순간 `traceId`가 사라진다.
  주문 생성 요청과 그로 인한 SSE 알림 로그를 **한 흐름으로 이어 볼 수 없다.**
  → `TaskDecorator`로 MDC를 전파하고, **전파 여부를 테스트로 검증**한다.
- ⚠️ **`traceId`가 응답으로 나가지 않는다.** 사용자가 오류를 신고해도 해당 요청의 로그를 특정할 수 없다.
  응답 헤더 또는 envelope에 노출할지는 **ADR로 결정**한다 (14.2와 함께 다룬다).
- 아웃박스를 거치는 이벤트는 **요청과 발행이 다른 시점·다른 스레드**다. 흐름을 잇고 싶다면 `traceId`를 페이로드에 실어야 한다 — Read Model 도입 시 함께 설계한다.

### 15.3 지표

- Actuator + Micrometer(Prometheus)가 이미 붙어 있다. `/actuator/prometheus`는 지정 IP만 접근 가능하다.
- **성능 작업의 근거는 로그가 아니라 지표여야 한다.** 최소한 다음은 관측할 수 있어야 한다:
  응답시간 분포(p50/p95/p99), HikariCP 커넥션 풀 사용률·대기, JVM 힙·GC, Redis 커넥션.
- `@TimeTrace`(`global/util/timetrace`)로 개별 메서드 실행 시간을 찍을 수 있다. **병목 후보를 좁힐 때 쓰고, 상시로 남발하지 않는다** (로그량이 곧 비용).
- **피크 전에 대시보드를 준비한다.** 장애가 난 뒤에 지표를 붙이면 늦다.

## 16. 외부 연동 격리 방침

현재 외부 의존은 **S3/MinIO**(이미지)와 **Anthropic API**(`global/ai/AnthropicClient` — 메뉴 다국어 번역) 둘이다.

- **타임아웃을 반드시 명시적으로 설정한다.** 무한 대기 금지. 외부 지연이 내부 스레드·커넥션 고갈로 전이되면 안 된다.
- **트랜잭션 안에서 호출하지 않는다** (9.4). 이미지 업로드·번역은 커넥션을 잡은 채 할 일이 아니다.
- **외부 장애가 핵심 기능을 막지 않게 한다.**
  - 번역 실패 → 한국어로 폴백하고 나중에 채운다. `booth_menu_dictionary`가 이미 재호출을 줄이는 캐시 역할을 한다.
  - 이미지 업로드 실패 → 부스·메뉴 등록 자체가 실패해야 하는지, 이미지만 비워 두고 성공시킬지 기능별로 정하고 **LLD에 명시**한다.
  - **주문 생성 경로에는 외부 호출을 넣지 않는다.** 피크에 가장 중요한 쓰기 경로다.
- **서킷브레이커·재시도**는 Resilience4j가 이미 있다(`FallbackIdempotencyStrategy`가 사용 중). 새 연동에 적용할 때 임계값은 ADR로 확정한다.
- **재시도는 상대가 멱등할 때만** 한다. 지수 백오프 + 최대 횟수 제한을 둔다.
- 외부 호출 로그에는 **소요 시간**을 남긴다.

## 17. 성능 검증·실측 방침 (이 프로젝트의 핵심)

### 17.1 측정 없이 최적화하지 않는다

- **"느릴 것 같아서" 고치지 않는다.** 재현 가능한 측정으로 병목을 특정한 뒤에 고친다.
- **"빨라졌을 것 같다"로 끝내지 않는다.** 같은 조건에서 다시 재고 Before/After를 ADR에 남긴다.
- 측정 조건이 다른 Before/After는 **비교가 아니라 소설이다.** 데이터 규모·분포·하드웨어·워밍업 여부를 함께 기록한다.

### 17.2 측정 항목 (최소 세트)

| 항목 | 내용 |
|---|---|
| 데이터 조건 | 테이블별 건수 + 분포 (3.1의 사용자 지정 조건) |
| 부하 조건 | 동시 사용자 수, 지속 시간, 워밍업 |
| 응답시간 | **p50 / p95 / p99** — 평균만 적지 않는다. 평균은 꼬리 지연을 숨긴다 |
| 처리량 | TPS |
| 에러율 | 특히 타임아웃·커넥션 고갈 |
| 쿼리 | `EXPLAIN` 실행 계획, 스캔 행 수 |

### 17.3 측정 환경

- **인메모리 DB로 성능을 재지 않는다.** 실행 계획과 락 동작이 다르다. MySQL(Testcontainers 또는 로컬 Docker)을 쓴다.
- **워밍업 후에 측정한다.** JIT 컴파일과 버퍼 풀 적재 전 수치는 의미가 없다.
- 측정 환경(로컬/CI/서버)을 기록한다. **다른 환경의 수치를 섞어 비교하지 않는다.**

### 17.4 회귀 방지

- 성능 개선 후 **그 조건을 재현하는 스크립트를 남긴다.** 다음 변경이 성능을 되돌려도 알 수 없으면 개선이 유지되지 않는다.
- 인덱스가 실제로 쓰이는지 검증하는 테스트(`EXPLAIN` 결과 확인)를 넣을 수 있다면 넣는다.

## 18. 방침 변경 절차

1. 변경 필요성을 **이슈로 등록**한다.
2. **ADR로 변경 결정과 근거를 기록**한다. 성능이 걸린 방침이면 실측치를 포함한다.
3. **본 문서의 해당 절을 갱신**하고 ADR 링크를 남긴다.
4. 변경이 기존 코드와 충돌하면 **마이그레이션 이슈를 분리 생성**한다.

- policy와 ADR이 충돌하면 **최신 ADR이 우선**하며, 그 ADR은 본 문서 갱신을 동반해야 한다.
- **"⚠️ 해결 대상"으로 표시된 항목이 해결되면 그 표시를 지우고**, 어떻게 해결했는지(ADR/이슈 번호)를 한 줄 남긴다.
