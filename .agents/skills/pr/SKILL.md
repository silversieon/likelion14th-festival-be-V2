# PR 생성 스킬

## 목적

모든 변경은 PR을 통해 기본 브랜치에 병합한다. PR은 이슈 → 설계 문서 → 구현 → 커밋으로 이어진 작업의 최종 산출물이며,
리뷰어가 **문서와 코드를 함께 검증**할 수 있도록 관련 링크를 모두 포함해야 한다.

## 이 스킬은 프로젝트에 종속되지 않는다

아래 값들은 **저장소마다 다르다. 하드코딩하거나 존재를 가정하지 않는다.**

| 값 | 확인 방법 | 없을 때 |
|---|---|---|
| **기본 브랜치** | `git symbolic-ref --short refs/remotes/origin/HEAD` → `origin/<기본브랜치>`<br/>또는 `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` | 확인될 때까지 PR을 만들지 않는다 |
| PR 템플릿 | `.github/pull_request_template.md` **또는** `.github/PULL_REQUEST_TEMPLATE.md` **또는** `.github/PULL_REQUEST_TEMPLATE/` 디렉터리 — **파일명 대소문자가 저장소마다 다르다** | 아래 "기본 본문 구조"를 쓴다 |
| 사용 가능한 라벨 | `gh label list` | 라벨 없이 생성한다 |
| 테스트 명령 | `AGENTS.md`의 검증 명령 절 → 없으면 빌드 파일로 판단 | 사용자에게 묻는다 |
| PR 생성 전 선행 작업 | `AGENTS.md` 워크플로에 정의되어 있으면 그것을 따른다 (예: 설계 문서 사본 동기화) | 없으면 생략 |

> **`main`을 base로 가정하지 않는다.** 기본 브랜치가 `develop`인 저장소가 흔하고, `main` 브랜치가 아예 없을 수도 있다.

## 실행 시점

- 이슈에 정의된 완료 조건(DoD)을 모두 충족하고, 커밋 스킬에 따라 커밋이 정리된 후 실행한다.
- **`AGENTS.md`에 PR 생성 전 선행 단계가 정의되어 있다면 먼저 완료**한다.
- PR 생성 전 프로젝트의 테스트 명령으로 **전체 통과를 다시 확인**한다.
- 사용자가 명시적으로 요청하지 않았다면 PR을 만들지 않는다.

## 브랜치 전략

- 작업 브랜치는 이슈 생성 직후 **기본 브랜치에서** 분기한다.

```
<type>/<이슈번호>-<간단한-설명(kebab-case, 영문)>
```

| type | 용도 |
|---|---|
| `feat` | 기능 개발 |
| `fix` | 버그 수정 |
| `refactor` | 리팩터링 |
| `perf` | 성능 개선 |
| `docs` | 문서 |
| `chore` | 그 외 |

> 예시 (형식 참고용): `feat/12-create-order`, `perf/23-order-list-index`

기존 브랜치 명명 관례가 있으면 그것을 우선한다 — `git branch -a`로 확인한다.

## PR 작성 규칙

### 1. 제목

커밋 컨벤션과 동일한 형식(깃모지 포함)을 사용한다.

```
<gitmoji> <type>(<scope>): <요약> (#<이슈번호>)
```

- gitmoji는 commit 스킬의 type별 깃모지 표를 따른다 (✨ feat / 🐛 fix / ♻️ refactor / 📝 docs / ✅ test / 🔧 chore / ⚡️ perf …)

### 2. 본문

**저장소에 PR 템플릿이 있으면 그 양식을 그대로 따른다.** 템플릿 섹션을 임의로 삭제하지 않고, 해당 없는 섹션은 "해당 없음"으로 명시한다.

템플릿 유무와 관계없이 **다음은 반드시 포함**한다.

| 항목 | 내용 |
|---|---|
| **관련 이슈** | `Closes #<이슈번호>` — 머지 시 이슈가 자동으로 닫히도록 키워드를 사용한다 |
| **관련 문서** | 이 작업에서 작성/수정한 설계 문서(ADR·LLD 등)의 경로 링크. 없으면 **없는 사유**를 명시한다 |
| **변경 요약** | 무엇을 왜 바꿨는지. 리뷰어가 diff를 열기 전에 맥락을 잡을 수 있어야 한다 |
| **테스트** | 어떤 테스트로 무엇을 검증했는지와 **실행 결과**. TDD로 구현했다면 설계 문서의 테스트 계획이 모두 소화되었는지 |
| **리뷰 포인트** | 특히 봐줬으면 하는 부분, 판단이 갈릴 수 있었던 선택 |

상황에 따라 추가한다:

- **스키마를 바꿨다면**: 마이그레이션 파일, 기존 데이터 백필 방법, 롤백 방법
- **성능 작업이라면**: Before/After 수치와 **측정 조건** (수치만 적고 조건을 빼면 비교가 성립하지 않는다)
- **호환성이 깨진다면**: 무엇이 깨지고 클라이언트가 무엇을 고쳐야 하는지

### 3. 라벨

`gh label list`로 확인한 **실제 존재하는 라벨만** 부여한다. 보통 이슈와 동일한 유형/도메인 라벨을 쓴다.

### 4. 크기

- PR 하나는 하나의 이슈만 해결한다.
- 리뷰 가능한 크기(변경 파일 기준 대략 20개 이하)를 유지한다. 커지면 이슈를 분할해 별도 PR로 나눈다.
- 포매터·린터가 자동으로 건드린 무관한 파일이 섞였다면 본문에 그 사실을 밝힌다.

## 실행 방법

```bash
# 1) 기본 브랜치와 템플릿, 라벨을 먼저 확인한다
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
ls .github/ | grep -i pull_request      # 파일명 대소문자 확인
gh label list

# 2) 푸시 후 생성
git push -u origin <작업 브랜치>

gh pr create \
  --title "<제목>" \
  --body-file <본문 파일> \
  --base "<확인한 기본 브랜치>" \
  --label "<gh label list에서 확인한 라벨>"
```

## 체크리스트

- [ ] 기본 브랜치를 **명령으로 확인**했는가 (`main`이라고 가정하지 않았는가)
- [ ] PR 템플릿 파일명을 **대소문자까지 실제로 확인**했는가
- [ ] `AGENTS.md`에 정의된 PR 생성 전 선행 단계를 완료했는가
- [ ] 브랜치 이름이 `<type>/<이슈번호>-<설명>` 형식인가
- [ ] 제목이 `<gitmoji> type(scope): 요약 (#이슈번호)` 형식인가 (깃모지 필수)
- [ ] 본문에 `Closes #<이슈번호>`가 포함되었는가
- [ ] 관련 설계 문서 링크가 포함되었는가 (없다면 사유 명시)
- [ ] 테스트 전체 통과 결과를 본문에 기재했는가
- [ ] 스키마 변경 / 성능 수치 / 호환성 파괴가 있다면 해당 내용을 본문에 적었는가
- [ ] `gh label list`로 확인한 라벨만 부여했는가
