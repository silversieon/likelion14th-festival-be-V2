## 컨텍스트 (Context)

### 요구사항 (사용자 지시 원문)

> "주문 기준 대용량 데이터를 삽입하려고해. 그런데 그냥 데이터를 많이 넣는게 아니라 특정 조건을 기준으로 넣으려고해. (…) 우선 학교 핫스팟이야. 모든 학교에 주문을 골고루 분포시키는게 아니라 Hot 그룹 5개교 50%, Warm 그룹 50개교 35% 기타 15%로 할 것이며, Hot School 5개교 하위 부스 중 인기 부스 3개가 해당 학교 주문의 70%, 그 외 부스가 30%를 맡으면 좋겠어. 메뉴에도 핫스팟이 있어. 모든 Booth 의 대표 메뉴 (2개)가 해당 부스의 주문 65%를 차지하고, 나머지가 35%를 차지해야해. 주문의 상태도 비중이 나뉘어. 대기중 5%, 조리 중 10% 완료된 75% 취소 된 10%여야하며, 주문 하나가 가지는 메뉴 개수는 1~4개 정도로 분포해야해. (…) 대용량 데이터는 한 번 넣을게 아니라 계속 조건에 부합하게 (주문 기준) 5만 건, 10만 건, 50만 건, 100만 건, 500만 건 이렇게 늘려서 넣을 거야."

이후 대화에서 확정된 세부 조건 (개발자 답변 기준, 원문 전체는 LLD 9장에 인용한다):

| 항목 | 확정 내용 |
|---|---|
| 대표 메뉴 65%의 기준 | **판매 수량**(`SUM(quantity)`) |
| 대표 메뉴 2개 | 부스마다 임의 식별자로 **고정**. 단, 서경대는 기존 판매 수량 상위 2개 |
| Hot 5개교 | 서경대(1)·성신여대(172)·한성대(343)·덕성여대(103)·광운대(46) |
| Warm | Hot을 제외한 **서울 소재 전부** — 실제 48개교 (서울 53 − Hot 5) |
| 기타 | 나머지 306개교 |
| Warm·기타 안의 배분 | 학교 간 균등, 학교 안 부스 간 균등 |
| Hot 인기 부스 3곳 | 서경대는 기존 주문 상위 3곳, 나머지 4개교는 임의 고정 |
| 주문당 메뉴 수 | 1개 10% / 2개 25% / 3개 50% / 4개 15%, 주문 안 중복 금지, **주문 1건 = 부스 1곳** |
| 항목당 수량 | 서경대 축제 기간(5/13~15) 실측: 1개 93.04% / 2개 5.68% / 3개 0.89% / 4개 0.32% / 5개 0.03% / 10개 0.03% |
| 시각 | 학교마다 연속 3일, 5월 2주~6월 1주 평일에 분산 (서경대는 기존 5/13~15). 날짜 비중 20/42/38%, 시간대 비중은 서경대 실측 |
| 축제 일정 저장 | `booth_operation`에 학교별 3일 일정 생성 (A안), 운영 시간은 하루 종일 |
| 단계 | **누적 합계** 5만 → 10만 → 50만 → 100만 → 500만 |
| 기존 서경대 주문 | **보존**. 단계마다 "목표 누적 − 현재 건수"만 생성(쿼터 차감)해 누적 합계가 항상 비율을 지킨다 |
| 제외 | 품절 메뉴, 0원 메뉴, 주문 가능 메뉴 2개 미만 부스 |
| 기타 값 | 고객명 약 500개 이름 풀, 전화번호 `010-XXXX-XXXX` 무작위, 테이블 1~30, 인원 1~6, 취소 사유 균등 |
| 사전 준비 | 모든 부스를 `OPEN` + `order_enabled = 1`로 바꾼다 |

### 이 결정이 필요한 이유

ADR-0002·0003은 부스·메뉴·매니저를 Flyway 마이그레이션(앱 기동 시 `db/migration`의 `V{N}__*.sql`을 번호 순으로 한 번씩 실행하는 방식)으로 넣었다. 주문은 세 가지가 다르다.

1. **양** — 최종 단계에서 `orders` 500만, `order_items` 약 1,350만, `order_item_units` 약 1,470만 행이다 (아래 행 증폭). Flyway 파일 하나 = 트랜잭션 하나라서 이 양을 한 파일로 넣을 수 없다.
2. **분포** — 학교·부스·메뉴 3단계 핫스팟, 상태 비율, 메뉴 개수 비율, 수량 분포, 시각 분포를 **동시에, 정확히** 맞춰야 한다. 가중치 샘플링(비율에 따라 무작위로 고르는 것)과 쿼터 계산(목표 건수를 먼저 정확히 나눠 두는 것)이 필요하다.
3. **단계 적재** — 한 번이 아니라 5번 늘려 넣는다. 매 단계 누적 합계가 비율을 지켜야 하고, 단계 단위로 되돌릴 수 있어야 한다.

기존 방식과 비교하면: ADR-0002는 "SQL 한 문장(`INSERT ... SELECT`)으로 DB 안에서 생성"이었다. 이번에는 **DB 밖(Python)에서 행을 만들고 파일로 넣는** 방식을 검토한다.

### 행 증폭 (policy 3.2)

주문 1건 → 항목 N개 → 수량 합만큼 단위(`order_item_units`). 확정 분포로 계산하면

- 주문당 항목 수 기댓값 = 1×0.10 + 2×0.25 + 3×0.50 + 4×0.15 = **2.70**
- 항목당 수량 기댓값 = **1.088** (서경대 실측)

| 누적 단계 | `orders` | `order_items` (×2.70) | `order_item_units` (×2.94) | 이번 단계 추가분 (주문) |
|---|---|---|---|---|
| 1 | 50,000 | 약 13.5만 | 약 14.7만 | 47,705 (기존 2,295 차감) |
| 2 | 100,000 | 약 27만 | 약 29.4만 | 50,000 |
| 3 | 500,000 | 약 135만 | 약 147만 | 400,000 |
| 4 | 1,000,000 | 약 270만 | 약 294만 | 500,000 |
| 5 | 5,000,000 | 약 1,350만 | 약 1,470만 | 4,000,000 |

> 기존 서경대 주문은 항목 수 평균이 1.64라서 위 기댓값보다 작다. 메뉴 개수 비율은 **전체 주문 기준**으로 맞추므로 신규 생성분이 이를 보정한다.

그 밖에 `booth_operation` 약 4.2만 행(약 1.4만 부스 × 3일)을 1회 적재한다.

### 측정된 현상

적재 방식별 속도를 운영 테이블과 분리된 임시 스키마(`bench_tmp`)에서 재었다. 측정 후 스키마와 파일은 삭제했다.

| 항목 | 값 |
|---|---|
| 대상 | `orders` 구조 복제 테이블 + `order_items` 형태 테이블(FK → orders, ON DELETE CASCADE) |
| 데이터 규모 | 주문 100,000 / 항목 269,943 (메뉴 수 분포 10/25/50/15% 적용) |
| 측정 조건 | 로컬 Docker MySQL 8.0.46, 버퍼 풀 2,048MB(설정값 1228M이 청크 단위로 올림된 값 — 아래 주석),  `innodb_flush_log_at_trx_commit=1`, binlog 켜짐, 앱 3대 기동 중, 3회 측정 |
| 생성 파일 크기 | CSV: orders 11.6MB + items 8.3MB / INSERT SQL: 22.3MB |
| **`LOAD DATA INFILE`, FK 켬** | 2.28 / 2.34 / 2.32초 → **평균 2.31초** |
| **`LOAD DATA INFILE`, FK 끔** | 2.24 / 2.16 / 2.16초 → **평균 2.19초** (FK 켬 대비 −5%) |
| **다중 행 INSERT (1,000행/문장), FK 켬** | 3.79 / 4.07 / 3.86초 → **평균 3.91초** |
| 현재 주문 데이터 | `orders` 2,259 / `order_items` 3,634 / `order_item_units` 3,955 (약 3MB) |
| 디스크 여유 | 924GB |

해석:

> 버퍼 풀 주석: compose는 `--innodb_buffer_pool_size=1228M`이지만, MySQL은 버퍼 풀 크기를 `innodb_buffer_pool_chunk_size`(128MB) × `innodb_buffer_pool_instances`(1GB 이상이면 기본 8) = **1,024MB의 배수로 올림**한다. 그래서 실제 값이 2,048MB가 되었고, 컨테이너 메모리 한도(2G)와 같아졌다. 이 설정 문제는 이 ADR과 별개로 처리한다.

- **`LOAD DATA`가 다중 행 INSERT보다 약 1.7배 빠르다.** 파일 크기도 CSV가 약 10% 작다. `LOAD DATA`는 SQL 문장을 해석하지 않고 행을 바로 밀어 넣기 때문이다.
- **FK를 꺼서 얻는 이득은 이 규모에서 5% 정도로 작다.** 다만 이 측정은 테이블이 버퍼 풀(InnoDB가 데이터·인덱스를 메모리에 올려두는 캐시) 안에 다 들어가는 크기였다. 500만 단계(데이터+인덱스 수 GB)에서는 FK 검사가 부모 행을 디스크에서 읽어야 하므로 차이가 커질 수 있다 — 구현 후 단계별로 실측해 결과 절에 남긴다.
- 100,000건 기준 선형 외삽(실제로는 버퍼 풀을 넘으면 느려진다): 5단계 추가분(주문 400만 + 항목 1,080만 + 단위 1,170만)은 **수 분 단위**로 예상된다. 어느 방식이든 "가능한가"가 아니라 **분포를 얼마나 정확히, 재현 가능하게 맞추는가**가 결정의 핵심이다.

## 결정 동인 (Decision Drivers)

1. **분포 정확도** — 학교·부스·메뉴(수량)·상태·메뉴 개수 비율을 매 단계 누적 기준으로 정확히 맞출 것. 측정 근거가 되는 데이터라 비율이 흔들리면 Before/After 비교가 성립하지 않는다 (policy 18.1)
2. **재현성** — 같은 입력이면 같은 데이터가 나올 것 (시드 고정). 단계 적재를 다른 환경에서 다시 할 수 있어야 한다
3. **단계 롤백** — 한 단계만 지우고 다시 넣을 수 있을 것
4. **적재 속도** — 500만 단계가 수십 분 안에 끝날 것
5. **구현·검증 난이도** — 생성 규칙을 읽고 고치기 쉬울 것

## 고려한 옵션 (Considered Options)

### 옵션 1: 집합 기반 SQL로 DB 안에서 생성 (`INSERT ... SELECT`)

- 설명: ADR-0002와 같은 방식. 숫자 시퀀스 테이블과 `ROW_NUMBER()`·`MOD()`로 학교·부스·메뉴·상태를 배정하는 SQL을 단계별로 실행한다. 서경대 기존 주문을 복제해 늘리는 변형도 여기에 속한다.
- 장점:
  - 데이터가 DB 밖으로 나가지 않는다. 파일 복사(`docker cp`) 단계가 없다
  - 적재 속도가 가장 빠를 수 있다 (ADR-0002 실측: 메뉴 14만 행 2.4초)
- 단점:
  - **3단계 핫스팟 + 쿼터 차감 + 시각 분포를 SQL로 표현하기 매우 어렵다.** 가중치 배정을 `CASE`와 누적 비율 구간으로 일일이 써야 하고, 주문 1건에 메뉴를 중복 없이 1~4개 고르는 것은 SQL로 특히 까다롭다
  - 생성 규칙을 바꾸면 SQL 여러 개를 함께 고쳐야 한다 → 검증 난이도가 높다
  - 원본 행에 공유 잠금(다른 트랜잭션이 그 행을 수정하지 못하게 거는 읽기 잠금)이 걸려, 매분 `booth`를 UPDATE하는 스케줄러(`BoothScheduler`)와 부딪칠 수 있다 (ADR-0002에서 확인한 문제)
  - 서경대 복제 변형은 학교 수가 고정이라 82만 건 근처에서 한계가 온다
- 예상/실측 효과: 속도는 가장 좋을 수 있으나 측정하지 않았다 — 분포 표현이 어렵다는 이유로 대화 단계에서 탈락

### 옵션 2: Python 생성기 + 다중 행 INSERT (배치 삽입)

- 설명: Python이 분포대로 행을 만들고, 1,000행씩 묶은 `INSERT ... VALUES (...),(...)` 문장으로 보낸다. 배치 삽입(insert를 한 건씩 보내지 않고 여러 건을 묶어 한 번에 보내 왕복 횟수를 줄이는 방식)이다.
- 장점:
  - 분포 로직을 Python으로 자유롭게 쓴다 (가중치 샘플링·쿼터·중복 없는 메뉴 선택이 쉽다)
  - 파일을 컨테이너에 복사할 필요가 없다 (`mysql` 클라이언트로 바로 실행)
- 단점:
  - **`LOAD DATA`보다 약 1.7배 느리다** (실측 3.91초 vs 2.31초)
  - SQL 문자열 이스케이프(따옴표·특수문자 처리)를 직접 책임져야 한다
  - 생성 파일이 CSV보다 크다 (22.3MB vs 19.9MB)
- 예상/실측 효과: 10만 주문 + 27만 항목 **3.91초**

### 옵션 3: Python 생성기 + CSV + `LOAD DATA INFILE` — **권고안**

- 설명: Python이 분포대로 행을 만들어 **테이블별 CSV**로 쓰고, 컨테이너의 `secure_file_priv` 경로(`/var/lib/mysql-files`, MySQL이 서버 쪽 파일 읽기를 허용한 유일한 폴더)에 복사한 뒤 `LOAD DATA INFILE`로 넣는다.
- 장점:
  - 분포 로직은 옵션 2와 같이 Python으로 쓴다
  - **가장 빠르다** (실측 2.31초, FK 끔 2.19초)
  - 같은 CSV를 다시 적재하면 결과가 똑같다 → 재현성과 롤백 후 재적재가 쉽다
  - 생성(파일 만들기)과 적재(DB에 넣기)가 분리되어, 적재 전에 파일만으로 분포를 검증할 수 있다
- 단점:
  - 파일 복사 단계(`docker cp`)가 추가된다
  - 클라이언트 쪽 `LOAD DATA LOCAL`은 `local_infile=0`이라 쓸 수 없다 → 서버 쪽 경로만 쓴다
  - CSV의 NULL(`\N`)·줄바꿈·인코딩(`utf8mb4`) 규칙을 지켜야 한다
- 예상/실측 효과: 10만 주문 + 27만 항목 **2.31초** (FK 끔 2.19초)

### 비교 요약

| 기준 | 옵션 1 집합 기반 SQL | 옵션 2 Python + 배치 INSERT | 옵션 3 Python + CSV + LOAD DATA |
|---|---|---|---|
| 분포 정확도 (3단계 핫스팟·쿼터) | 표현 매우 어려움 | 쉬움 | 쉬움 |
| 재현성 | 결정적 함수로 가능 | 시드 고정 | 시드 고정 + **같은 파일 재적재** |
| 적재 속도 (10만 주문 실측) | 미측정 (빠를 것) | 3.91초 | **2.31초** |
| 단계 롤백 | 조건 DELETE | ID 구간 DELETE | ID 구간 DELETE |
| 추가 절차 | 없음 | 없음 | `docker cp` |
| 구현·검증 난이도 | 높음 | 보통 | 보통 |

## 결정 (Decision)

**확정**: 옵션 3 (개발자 승인 2026-10-12) — 권고안과 같다. 적재 중 FK는 켠 채로 넣는다. 실측 이득(10만 건 규모 5%)보다 적재 시점에 참조 무결성을 DB가 보장하는 쪽을 택했다.

**권고안 이력**: 옵션 3 — 분포 정확도(동인 1)는 Python으로만 현실적으로 맞출 수 있고, 그중 `LOAD DATA`가 실측으로 가장 빠르며(동인 4), 같은 CSV를 다시 넣으면 결과가 같아 재현성·롤백(동인 2·3)이 가장 쉽다. 작성 당시 구현 규칙은 사전 논의대로 "FK 끄고 적재 후 켜기"였다.

### 구현 규칙

**위치·도구**
- 생성기·적재·검증 스크립트는 `scripts/seed/order/`에 둔다 — 기존 `scripts/seed/booth-manager/`와 같은 규칙 (policy 3.3, AGENTS.md 3.3)
- 생성기는 **Python 3** (표준 라이브러리만 사용 목표), **난수 시드를 고정**하고 시드 값을 실행 기록에 남긴다

**적재 순서 (사전 준비 1회 → 단계 반복)**
1. **사전 준비 (1회)** — 모든 부스 `booth_status = 'OPEN'`, `order_enabled = 1` / 고정 목록(Hot 인기 부스, 부스별 대표 메뉴 2개, 학교별 축제 날짜)을 생성해 파일로 저장·커밋
2. **축제 일정 (1회)** — 서경대를 제외한 모든 부스에 학교별 3일 `booth_operation` 행(`ALL`, 하루 종일)을 같은 CSV 방식으로 적재
3. **단계 적재 (5회)** — 셀(학교·부스·메뉴·상태)별로 **"목표 누적 − 현재 DB 건수"** 를 계산해 그만큼만 생성
4. **검증** — 비율·정합성 SQL 실행, 결과 기록

**분포**
- 학교 그룹·부스·상태·메뉴 개수는 **쿼터 방식**(목표 건수를 먼저 정확히 계산한 뒤 섞기)으로 정확히 맞춘다. 시각·수량·고객 정보 같은 세부 값만 가중치 무작위로 뽑는다
- 대표 메뉴 65%는 **판매 수량 기준**으로, 부스 단위로 맞춘다
- 메뉴 개수·상태 비율은 **전체 주문 기준**으로 맞춘다 (기존 서경대 주문 때문에 학교 단위로는 맞출 수 없다)

**트랜잭션·파일 단위**
- 주문 **10만 건 단위로 CSV를 나누고**, 파일 하나 = `LOAD DATA` 한 번 = 자동 커밋 한 번으로 끊는다 ("전부 한 트랜잭션" 금지, policy 3.3)
- 같은 묶음은 `orders` → `order_items` → `order_item_units` 순으로 넣는다
- 중간에 실패하면 실패한 묶음의 ID 구간만 지우고 그 묶음부터 다시 넣는다

**ID·FK**
- ID는 생성기가 **직접 배정**한다 (현재 `max(id)+1`부터). 단계별 ID 구간을 실행 기록에 남긴다
- **FK 검사는 켠 채로 적재한다** (`foreign_key_checks`를 건드리지 않는다, 개발자 지시). 잘못된 `order_id`·`booth_menu_id`는 적재 시점에 그 파일의 `LOAD DATA`가 실패하는 것으로 드러난다 → 해당 묶음만 고쳐 다시 넣는다
- 보조 인덱스는 그대로 둔다 (`orders`에는 원래 보조 인덱스가 없다)

**롤백**
- 단계 롤백은 기록된 **ID 구간 DELETE**로 한다. 대량 삭제는 자식부터(`order_item_units` → `order_items` → `orders`) 구간을 나눠 지운다 — CASCADE에 맡기면 한 문장이 수백만 행을 잠근다

**제외·정합성**
- `idempotency`·`outbox`에는 아무것도 넣지 않는다 (policy 3.4)
- `menu_price` = 적재 시점 메뉴 가격, `total_order_item_price` = 수량 × 가격, `total_order_price` = 항목 합계의 합
- 상태별 컬럼 규칙:

| 상태 | `completed_at` | `canceled_at` / `order_cancel_reason` | `is_served` | `modified_at` |
|---|---|---|---|---|
| WAITING | NULL | NULL | 전부 false | `created_at` |
| COOKING | NULL | NULL | 일부 true (최소 1개 false) | `created_at` + 1~15분 |
| COMPLETED | `created_at` + 5~40분 | NULL | 전부 true | `completed_at` |
| CANCELED | NULL | `created_at` + 1~30분 / 4종 균등 | 전부 false | `canceled_at` |

### 긍정적

- 분포 규칙이 Python 코드 한 곳에 모여, 조건이 바뀌면 생성기만 고치면 된다
- 같은 시드·같은 CSV로 어느 환경에서든 같은 데이터를 재현할 수 있다
- 단계마다 쿼터를 다시 계산하므로, 이전 단계의 작은 오차도 다음 단계에서 메워진다

### 부정적 / 트레이드오프

- **FK를 켠 채로 넣으므로 FK를 끄는 것보다 느리다.** 10만 건 규모 실측 차이는 5%였고, 버퍼 풀을 넘는 500만 단계에서는 더 벌어질 수 있다 (단계별 소요 시간을 결과 표에 남긴다)
- `docker cp`로 파일을 옮기는 절차가 추가된다 (500만 단계 CSV는 수 GB 예상)
- **사전 준비의 `OPEN`은 오래 유지되지 않는다.** `BoothScheduler`가 매일 01:00 모든 부스를 `CLOSED`로 바꾸고, 매분 "오늘 운영 일정이 있는 부스"만 `OPEN`으로 바꾼다. CSV 적재는 부스 상태를 보지 않으므로 적재에는 영향이 없지만, 이후 주문 생성 API로 부하 테스트를 하려면 그날 날짜의 `booth_operation`이 따로 필요하다
- 축제 일정(`booth_operation`) 약 4.2만 행이 추가되어, 매분 도는 스케줄러 UPDATE의 조인 대상이 늘어난다
- 기존 서경대 주문 때문에 메뉴 개수·상태 비율은 학교 단위가 아니라 전체 기준으로만 맞는다

### 에이전트 → 개발자 확인 요청

1. **작성 완료 보고** — ADR-0004 「핫스팟 분포 주문 데이터는 Python 생성기 → CSV → `LOAD DATA INFILE`로 단계 적재한다」, `docs/adr/ADR-0004-order-bulk-load-with-csv-load-data.md`
2. **옵션 요약**
   - 옵션 1 (집합 기반 SQL): 파일 이동 없이 DB 안에서 끝나지만, 3단계 핫스팟·쿼터·중복 없는 메뉴 선택을 SQL로 표현하기 어려워 분포 정확도를 포기한다
   - 옵션 2 (Python + 배치 INSERT): 분포는 자유롭게 맞추고 파일 이동도 없지만, 실측 1.7배 느리다
   - 옵션 3 (Python + CSV + LOAD DATA): 분포·속도·재현성이 가장 좋고, 대신 `docker cp` 절차가 붙는다
3. **권고안과 근거** — 옵션 3. 개발자가 그대로 따를 필요는 없다
4. **판단이 필요한 열린 질문**
   - FK 끄기의 실측 이득이 10만 건 규모에서 5%로 작았다. 지시대로 "끄고 적재 후 켜기"로 가되, 단계별 실측으로 이득이 계속 작으면 켠 채로 바꿀지
   - 스크립트 위치를 처음 제안한 `scripts/bulk-load/` 대신 기존 관례인 `scripts/seed/order/`로 해도 되는지
   - 단계 사이에 쿼리 재측정(작업 갈래 ③의 Before)을 이 이슈에서 할지, 별도 이슈로 뺄지
