# Commit 스킬

## 목적

커밋 이력만 보고도 변경의 의도와 범위를 파악할 수 있도록, 모든 커밋은 **gitmoji + Conventional Commits** 규칙을 따른다.

## 이 스킬은 프로젝트에 종속되지 않는다

아래 값들은 **저장소마다 다르므로 하드코딩하지 않는다.** 커밋 전에 실제 값을 확인한다.

| 값 | 확인 방법 |
|---|---|
| scope로 쓸 도메인·영역 이름 | `AGENTS.md`(또는 `CONTRIBUTING.md`)에 정의되어 있으면 그것을 따른다. 없으면 **소스 트리의 최상위 도메인/모듈 디렉터리 이름**을 쓴다 |
| 테스트 명령 | `AGENTS.md`의 검증 명령 절 → 없으면 빌드 파일로 판단 (`gradlew test` / `mvn test` / `npm test` / `pytest` …) |
| 커밋 메시지 언어 | 기존 `git log`의 다수 언어를 따른다 |
| 기존 메시지 관례 | **`git log --oneline -20`을 먼저 확인**한다. 기존 이력과 다른 형식을 새로 도입하지 않는다 |

> 기존 이력과 이 문서의 형식이 다르면 **사용자에게 어느 쪽을 따를지 확인**한 뒤 진행한다. 말없이 형식을 바꾸지 않는다.

## 실행 시점

- 하나의 논리적 작업 단위(도메인 모델 추가, 서비스 구현, 컨트롤러·인프라 구현, 테스트 추가 등)가 완료되고 **컴파일과 테스트가 통과한 상태**에서 실행한다.
- 커밋 전 프로젝트의 테스트 명령으로 통과를 확인한다. **실패한 상태로 커밋하지 않는다.**
- 사용자가 명시적으로 요청하지 않았다면 커밋하지 않는다.

## 메시지 형식

```
<gitmoji> <type>(<scope>): <subject>

<body>

<footer>
```

### gitmoji + type (필수)

**subject 맨 앞에 type과 짝이 되는 깃모지를 붙인다.** (gitmoji.dev 표준 준수)

| gitmoji | type | 용도 |
|---|---|---|
| ✨ | `feat` | 새로운 기능 (유스케이스, API, 도메인 로직 추가) |
| 🐛 | `fix` | 버그 수정 |
| ♻️ | `refactor` | 동작 변경 없는 구조 개선 |
| ✅ | `test` | 테스트 코드 추가/수정 |
| 📝 | `docs` | 문서 작성/수정 (ADR, LLD, API 스펙, README 등) |
| 🔧 | `chore` | 빌드 설정, 환경 설정 파일 등 코드 외 작업 |
| 🎨 | `style` | 포맷팅, 코드 구조 정리 등 로직에 영향 없는 변경 |
| ⚡️ | `perf` | 성능 개선 |

상황이 더 구체적이면 같은 type이라도 아래 깃모지로 대체할 수 있다:

| gitmoji | 상황 (type) |
|---|---|
| 🎉 | 프로젝트 최초 시작 (`chore`) |
| ⬆️ / ⬇️ | 의존성 업그레이드 / 다운그레이드 (`chore`) |
| ➕ / ➖ | 의존성 추가 / 제거 (`chore`) |
| 👷 | CI 구성 (`chore`) |
| 🚑️ | 긴급 핫픽스 (`fix`) |
| 🔒️ | 보안 이슈 수정 (`fix`) |
| 🗃️ | DB 스키마 변경 (`feat`/`fix`) |
| 🌱 | 시드/더미 데이터 (`chore`/`feat`) |
| 🔀 | 조회·저장 구조 분리 등 아키텍처 변경 (`refactor`) |
| 💥 | 호환성 깨지는 변경 (BREAKING CHANGE footer와 함께) |
| 🔥 | 코드/파일 제거 (`refactor`/`chore`) |
| 🚚 | 파일/패키지 이동·이름 변경 (`refactor`) |

### scope (필수)

**이 저장소의 도메인 또는 영역 이름**을 쓴다. 목록은 `AGENTS.md`에 정의되어 있으면 그것을, 없으면 소스 트리의 도메인 디렉터리 이름을 따른다.
코드 외 작업은 `build`, `ci`, `docs`, `deps` 등을 쓴다.

> 임의로 새 scope를 만들지 않는다. 기존 `git log`에 쓰인 scope를 먼저 확인한다.

### subject (필수)

- 50자 이내, 마침표 없이 종결한다.
- "무엇을 했는지"를 명령형/명사형으로 작성한다. ("~추가", "~수정", "~구현")

### body (선택)

- "왜" 이 변경이 필요했는지, 어떤 접근을 택했는지를 작성한다.
- 코드만 봐서는 알 수 없는 맥락(트레이드오프, 제약, 실측 근거)이 있을 때 반드시 작성한다.
- 성능 관련 커밋이면 **Before/After 수치**를 남긴다.
- 포매터·린터가 자동으로 건드린 파일이 섞였다면 그 사실을 한 줄 남긴다.

### footer (이슈 참조)

- 진행 중인 이슈: `Refs: #<이슈번호>`
- 이슈를 완결하는 커밋: `Closes: #<이슈번호>` (일반적으로 PR 머지로 닫히므로 커밋에서는 `Refs` 권장)
- 호환성이 깨지는 변경: `BREAKING CHANGE: <설명>`

> 이슈 기반으로 운영하지 않는 저장소라면 footer를 생략한다. 이슈 번호를 **추측해서 적지 않는다.**

## 예시

> 아래는 **형식을 보여주기 위한 예시**다. scope와 내용은 실제 저장소의 것으로 바꿔 쓴다.

```
✨ feat(order): 주문 생성 유스케이스 구현

OrderService에 주문 생성 유스케이스를 추가한다.
주문번호 채번은 OrderNumberGenerator에 위임하여
채번 정책이 바뀌어도 서비스 코드를 고치지 않도록 했다.

Refs: #12
```

```
⚡️ perf(order): 주문 목록 조회에 복합 인덱스 적용

(status, created_at) 복합 인덱스를 추가한다.
status 단독 인덱스는 카디널리티가 낮아 효과가 없었고,
정렬까지 인덱스로 해결하려면 created_at이 뒤에 와야 했다.

Before: p95 4,200ms / full scan 1,000,000 rows
After:  p95 180ms  / ref 스캔 2,400 rows

Refs: #23
```

```
📝 docs(adr): 주문 조회 성능 개선 방식 결정 기록 (ADR-0007)

Refs: #23
```

## 커밋 단위 규칙

- **하나의 커밋 = 하나의 논리적 변경.** 서로 무관한 계층·기능의 변경이 뒤섞인 거대 커밋을 만들지 않는다.
- 설계 문서(ADR·LLD 등) 작성은 구현과 분리하여 `docs` 커밋으로 먼저 남긴다.
- **구현을 TDD로 진행하는 저장소라면, 커밋 단위는 완료된 TDD 사이클을 기준으로 한다.**
  - 하나의 사이클(또는 같은 대상에 대한 응집된 몇 개의 사이클)이 Green + Refactor까지 끝난 시점에 커밋한다.
  - 해당 사이클의 테스트 코드와 구현 코드는 **같은 커밋에 포함**한다. (테스트만 있는 Red 상태로 커밋하지 않는다)
  - Refactor 결과가 크거나 기존 코드까지 건드렸다면 `refactor` 타입으로 분리 커밋한다.
- 리팩터링과 기능 추가를 한 커밋에 섞지 않는다.
- 스키마 변경(마이그레이션 파일)은 그 스키마를 사용하는 코드와 **같은 커밋**에 둔다. 따로 커밋하면 중간 커밋에서 애플리케이션이 기동하지 않는다.

## 브랜치 주의

- **기본 브랜치(default branch)에 직접 커밋하지 않는다.** 사용자가 명시적으로 허용한 경우에만 예외로 한다.
- 기본 브랜치 이름은 저장소마다 다르다 (`main` / `develop` / …). 다음으로 확인한다:
  ```bash
  git symbolic-ref --short refs/remotes/origin/HEAD   # → origin/<기본브랜치>
  ```

## 실행 방법

```bash
git status                 # 무엇이 변경되었는지 먼저 확인
git add <관련 파일만 선택>
git diff --staged          # 의도하지 않은 변경이 섞였는지 확인

# 여러 줄 메시지는 파일이나 heredoc으로 전달한다 (셸에 따라 인용 처리가 다르므로 주의)
git commit -F <메시지 파일>
```

- `git add .` 대신 **이번 커밋에 해당하는 파일만 명시적으로 스테이징**한다.
- 커밋 전 `git status`와 `git diff --staged`로 의도하지 않은 변경(빌드 산출물, IDE 설정, 포매터가 건드린 무관한 파일)이 섞이지 않았는지 확인한다.

## 체크리스트

- [ ] 프로젝트의 테스트 명령이 통과하는 상태인가
- [ ] `git log`로 기존 메시지 관례를 확인했는가
- [ ] subject 맨 앞에 type과 짝이 되는 깃모지가 있는가
- [ ] type과 scope가 이 저장소의 실제 체계에 맞는가
- [ ] subject가 50자 이내인가
- [ ] 이슈 기반 저장소라면 footer에 이슈 번호(`Refs: #N`)가 있는가
- [ ] 하나의 논리적 변경만 담고 있는가
- [ ] 스테이징된 파일에 불필요한 변경(빌드 산출물, IDE 설정 등)이 없는가
- [ ] 기본 브랜치에 직접 커밋하려는 것은 아닌가
