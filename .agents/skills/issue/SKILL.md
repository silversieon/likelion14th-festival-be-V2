# Issue 생성 스킬

## 목적

모든 개발 작업(기능 추가, 버그 수정, 리팩터링, 문서 작업)은 **구현을 시작하기 전에 반드시 GitHub 이슈로 등록**한다.
이슈는 작업의 단위이자 추적의 시작점이며, 이후 브랜치·커밋·PR·설계 문서가 모두 이 이슈 번호를 참조한다.

## 이 스킬은 프로젝트에 종속되지 않는다

아래 값들은 **저장소마다 다르다. 하드코딩하거나 존재를 가정하지 않는다.** 이슈를 만들기 전에 실제로 확인한다.

| 값 | 확인 방법 | 없을 때 |
|---|---|---|
| 이슈 템플릿 | `.github/ISSUE_TEMPLATE/` 디렉터리를 나열한다. `.md`·`.yml` 어느 쪽이든 있을 수 있고, 파일명에 이모지가 붙어 있을 수도 있다 | 아래 "기본 본문 구조"를 쓴다 |
| 사용 가능한 라벨 | **`gh label list`** 로 실제 등록된 라벨을 확인한다 | 라벨 없이 생성하고, 필요하면 사용자에게 라벨 생성 여부를 묻는다 |
| 도메인/영역 이름 | `AGENTS.md`(또는 `CONTRIBUTING.md`)에 정의되어 있으면 그것을. 없으면 소스 트리의 도메인 디렉터리 이름 | 제목에서 도메인 부분을 생략한다 |
| 기존 이슈 관례 | **`gh issue list --limit 20`** 으로 기존 제목 형식을 확인한다 | 아래 제목 컨벤션을 쓴다 |
| 설계 문서 필요 여부 판단 기준 | `AGENTS.md` 워크플로 | 아키텍처/기술 결정이 수반되는지로 판단 |

> **라벨 이름을 추측해서 넘기지 않는다.** `gh`는 존재하지 않는 라벨을 만나면 이슈 생성 자체를 실패시킨다.
> 라벨 이름에 이모지가 포함된 저장소가 많으므로 **`gh label list` 출력을 그대로 복사해 쓴다.**

## 실행 시점

- 사용자가 새로운 기능/수정/리팩터링을 요청했을 때, **코드를 작성하기 전에** 가장 먼저 실행한다.
- 하나의 이슈는 하나의 PR로 완결될 수 있는 크기여야 한다. 요구사항이 크면 이슈를 분할한다.

## 작성 규칙

### 1. 제목 컨벤션

기존 이슈 관례가 있으면 그것을 따른다. 없으면 아래를 쓴다.

```
<gitmoji> [<유형>] <도메인>: <요약>
```

- gitmoji: 유형과 짝이 되는 깃모지를 맨 앞에 붙인다 — ✨ Feature / 🐛 Bug / ♻️ Refactor / 📝 Docs / ✅ Test / 🔧 Chore
- 유형: `Feature` | `Bug` | `Refactor` | `Docs` | `Test` | `Chore`
- 도메인: 이 저장소의 도메인/영역 이름
- 요약: 간결하게, 명사형 종결 권장

> 예시 (형식 참고용 — 실제 도메인 이름으로 바꿔 쓴다):
> - `✨ [Feature] order: 주문 생성 유스케이스 구현`
> - `🐛 [Bug] auth: 만료 토큰으로 재발급 시 500 응답`
> - `♻️ [Refactor] user: 조회 서비스 분리`

### 2. 본문

**저장소에 이슈 템플릿이 있으면 그 필드 구조를 그대로 따른다.** 템플릿 섹션을 임의로 삭제하지 않고, 해당 없는 섹션은 "해당 없음"으로 명시한다.

템플릿이 없을 때의 기본 본문 구조:

| 섹션 | 내용 |
|---|---|
| 배경 / 문제 | 왜 이 작업이 필요한지. 버그라면 **재현 절차 + 기대 동작 + 실제 동작** |
| 작업 내용 | 무엇을 할 것인지 구체적인 작업 목록 (체크박스) |
| 완료 조건 (DoD) | 이슈를 닫을 수 있는 **검증 가능한** 조건 (테스트 통과, 문서 작성, 측정치 달성 등) |
| 설계 문서 필요 여부 | 아키텍처/기술 결정이 수반되면 `필요`로 표시하고 이유를 한 줄 남긴다 |
| 참고 자료 | 관련 이슈, 설계 문서, 외부 링크 |

- **DoD는 "구현 완료" 같은 문장을 쓰지 않는다.** 누가 봐도 참/거짓을 판정할 수 있게 쓴다.
- 성능 관련 이슈면 DoD에 **목표 수치와 측정 조건**을 넣는다.

### 3. 라벨

`gh label list`로 확인한 **실제 존재하는 라벨만** 사용한다. 일반적으로 다음 축이 있으면 각 1개 이상 부여한다.

- 유형 (`type:*` 계열)
- 도메인/영역 (`domain:*`, `area:*` 계열)
- 필요 시 우선순위, 설계 문서 필요 표시(`needs:*`), `breaking-change`

라벨 체계가 없는 저장소라면 라벨 없이 생성한다. **없는 라벨을 임의로 만들지 않는다** — 사용자에게 먼저 묻는다.

## 실행 방법

```bash
# 1) 무엇이 있는지 먼저 확인한다
ls .github/ISSUE_TEMPLATE/ 2>/dev/null
gh label list
gh issue list --limit 20

# 2) 본문을 파일로 작성한 뒤 생성한다
gh issue create \
  --title "<제목>" \
  --body-file <본문 파일> \
  --label "<gh label list에서 확인한 라벨>"
```

생성 후 **이슈 번호를 반드시 확인**하고, 이후 단계(브랜치 이름, 설계 문서, 커밋 footer, PR 본문)에서 해당 번호를 참조한다.

## 체크리스트

- [ ] `.github/ISSUE_TEMPLATE/`를 실제로 확인했는가 (있으면 그 양식을 따랐는가)
- [ ] `gh label list`로 실제 존재하는 라벨을 확인했는가 (추측한 라벨을 넘기지 않았는가)
- [ ] 기존 이슈의 제목 관례를 확인했는가
- [ ] 제목에 깃모지가 있고 유형·도메인이 드러나는가
- [ ] 완료 조건(DoD)이 검증 가능한 문장인가
- [ ] 설계 문서(ADR 등) 필요 여부를 판단해 본문/라벨에 표시했는가
- [ ] 하나의 PR로 완결 가능한 크기인가
- [ ] 생성된 이슈 번호를 이후 작업에서 참조할 수 있게 기록했는가
