## 컨텍스트 (Context)

### 요구사항 (사용자 지시 원문)

> "부스 인기 메뉴 검색과 부스별 매출 검색에서 검색어 조회 시 양쪽 와일드카드가 데이터가 많은 상황에서 조회 시간에 병목을 발생시키고 있어. 예를 들어 '대학'이라고 입력하면 모든 대학교가 조회되고, 대학교별 부스별 메뉴들이 대량으로 조인되면서 많은 데이터들이 불러와지고 있어. 와일드카드 기준을 우측으로 한 뒤에 필요 시 적절한 인덱스를 걸어서 조회 성능을 향상시켜줘. 추가로 커서 기반 페이징을 활용해서 지정 개수만큼 조회되게 해줘. 커서 기반 페이징 공통 패키지는 global/common/pagenation에 있고, OrderController를 보면 사용 예시가 있으니 활용해."

> 측정 기준 (개발자 지시): "지금 적재된 5만 기준으로 측정해줘"

### 대상 API (LLD-0005에서 만든 것)

| API | 현재 동작 |
|---|---|
| `GET /api/statistics/booths/search` (부스별 매출 검색) | 전체 부스 14,093개에 매출 순위를 매긴 파생 테이블을 만든 뒤, `universityName LIKE '%검색어%'`로 거르고 **전부** 반환. `rank`는 **전체 부스 기준** 순위 |
| `GET /api/statistics/booths/menus` (부스별 인기 메뉴 순위) | 메뉴 × 부스 × 학과 × 대학을 조인하고, 완료 주문 전체를 메뉴별로 집계한 파생 테이블을 붙인 뒤 `LIKE '%검색어%'`로 거르고 **전부** 반환 |

두 API 모두 응답이 `List`라 결과 크기에 상한이 없다.

**`EXPLAIN ANALYZE` 결과 — 현재 쿼리 (Before)**

| 쿼리 | 검색어 | 결과 행 | DB 실행 시간 | 그중 "완료 주문 전체 집계" |
|---|---|---|---|---|
| 부스별 매출 검색 | `대학` | 14,009 | 577 ms | 508 ms (order_items 101,138행 → 부스 7,027개) |
| 부스별 매출 검색 | `서경대학교` | 31 | 331 ms | 290 ms |
| 부스별 인기 메뉴 | `대학` | **140,022** | **1,560 ms** | 161 ms (→ 메뉴 27,842개) |
| 부스별 인기 메뉴 | `서경대학교` | 242 | 188 ms | 171 ms |

**실행 계획에서 확인한 병목 두 가지**

1. **학교명 조건이 인덱스를 전혀 쓰지 않는다.** `LIKE '%…%'`(앞에 와일드카드가 붙으면 인덱스의 정렬 순서를 쓸 수 없다)라서, 옵티마이저(쿼리 실행 방법을 고르는 MySQL 내부 엔진)는 `booth` 14,093행을 전부 조인한 **뒤에** 학교명을 한 행씩 비교한다. 정확한 이름 `서경대학교`를 넣어도 마찬가지다.
   `대학`은 359개 학교 중 **354개**에 걸린다. 그래서 인기 메뉴 API는 메뉴 14만 행을 정렬·직렬화해 내려보낸다.
2. **검색어와 상관없이 완료 주문 전체를 매번 집계한다.** 집계를 먼저 끝낸 파생 테이블(서브쿼리 결과를 임시 테이블로 만들어 두고 조인하는 방식)에 검색 조건이 전달되지 않는다. 결과가 31행뿐인 검색도 order_items 10만 행을 훑는 데 170~290 ms를 쓴다.
   **이 비용은 주문 건수에 비례한다.** 다음 적재 단계(누적 10만 → 500만)로 가면 그대로 커진다.

## 결정 동인 (Decision Drivers)

1. **주문 건수가 늘어도 응답시간이 버티는가** — 이번 측정은 5만 건 기준이지만 적재 계획은 500만 건까지다. 주문 수에 비례하는 비용이 남으면 다음 단계에서 다시 무너진다.
2. **응답 크기 상한** — 요구사항대로 `size`만큼만 내려간다.
3. **API 계약 변경 범위** — 검색 의미(부분 일치 → 접두 일치)와 응답 형태(`List` → `CursorPageResponse`)는 이미 바뀐다. 그 이상(정렬 기준, `rank`의 뜻)을 바꾸면 프런트 영향이 커진다.
4. **쓰기 경로 영향** — 인덱스를 늘리면 주문 생성(`order_items` INSERT)이 느려진다 (policy 5.4).

## 고려한 옵션 (Considered Options)

세 옵션 모두 **검색어는 접두 일치(`LIKE '검색어%'`)로 바꾸고**, 응답은 공통 패키지의 `CursorPageResponse{items, nextCursor, hasNext, size}`와 `CursorCodec`을 쓴다 (OrderController와 같은 방식). 다른 점은 **집계를 언제, 어디까지 하느냐**다.

키셋 커서(keyset cursor: "마지막으로 본 행의 정렬 키보다 뒤에 있는 행"을 `WHERE`로 바로 찾는 방식. `OFFSET`처럼 앞 행을 세지 않는다)를 쓴다.

### 옵션 1: 기존 쿼리 구조 유지 + 접두 일치 + 키셋 커서

- **설명**: 쿼리 모양은 그대로 두고 `LIKE`만 우측 와일드카드로 바꾼다. 결과 맨 끝에 커서 조건과 `LIMIT size + 1`을 붙인다.
  - 매출 검색: 정렬 `rank`, 커서 `(lastRank)`
  - 인기 메뉴: 정렬 `(학교명, 학과명, 부스 id, 메뉴 순위)`, 커서는 이 네 값
- **장점**: 변경이 가장 작다. 매출 검색의 **전체 부스 기준 `rank`와 매출순 정렬이 그대로 유지**된다.
- **단점**: **완료 주문 전체 집계가 페이지마다 그대로 돈다.** 다음 페이지를 읽을 때마다 같은 집계를 처음부터 다시 한다. 주문 건수에 비례하는 비용이 그대로 남는다.
- **실측 (프로토타입)**:
  - 인기 메뉴 `서경대학교`: 188 → **164 ms**. 학교명 조건은 인덱스 range 스캔(인덱스에서 범위의 시작점을 찾아 거기서부터 순서대로 읽는 방식)으로 바뀌었다(0.03 ms). 하지만 집계 162 ms가 남는다
  - 인기 메뉴 `한`(접두 일치에서 가장 넓은 한 글자 — 62개교, 부스 1,345개): **396 ms**. 옵티마이저가 `booth_menu` 14만 행 전체 스캔을 골랐다
  - 매출 검색: 순위를 매기려면 전체 부스를 집계해야 하므로 **330 ms 아래로 내려가지 않는다**

### 옵션 2: 페이지에 들어갈 부스를 먼저 고르고, 그 부스만 집계 (부스 우선 키셋)

- **설명**: 쿼리를 두 단계로 나눈다.
  1. **부스 페이지 선택** — `universities` → `departments` → `booth`를 이름 접두 일치로 좁히고 `(학교명, 학과명, 부스 id)` 순서로 `size + 1`개만 고른다. 커서는 이 세 값이다.
  2. **집계** — 고른 부스 id 목록(최대 `size`개)에 대해서만 `booth_menu` → `order_items` → `orders(COMPLETED)`를 집계한다.
  - 인기 메뉴: **페이지 단위는 "부스"**다. 부스 하나에 메뉴 전부(평균 10개)가 순위와 함께 붙는다. 부스 안 순위(`PARTITION BY 부스`)라서 그 부스의 메뉴만 집계해도 순위가 정확하다.
  - 매출 검색: 같은 방식으로 부스를 이름순으로 고르고 그 부스들의 매출만 집계한다. **따라서 정렬은 매출순에서 이름순으로 바뀌고, 전체 부스 기준 `rank`는 낼 수 없다** (전체 순위는 정의상 전체 부스를 집계해야 나온다).
- **장점**: 집계 범위가 **페이지 크기(부스 `size`개)로 묶인다.** 주문 건수가 늘어도 "그 부스들의 주문"만큼만 커진다. 이름 조건은 기존 UNIQUE 인덱스 3개를 그대로 탄다(인덱스 추가 불필요).
- **단점**: 매출 검색의 **정렬 기준과 `rank`의 의미가 바뀐다** (계약 변경). 쿼리가 두 번으로 나뉜다.
  주문이 몰린 Hot 부스가 페이지에 들어오면 그 부스들의 주문만큼은 읽어야 한다 (아래 80 ms).
- **실측 (프로토타입, size 20)**:

  | 검색어 | ① 부스 페이지 선택 | ② 페이지 부스 집계 | 비고 |
  |---|---|---|---|
  | `서경대학교` | 0.11 ms | **80 ms** | Hot 학교. 부스 20개의 order_items 25,575행을 읽는다 |
  | `한` | 3.3 ms | **4 ms** | 접두 일치 최악의 한 글자. 첫 페이지 부스들은 주문이 적다 |

  ① 실행 계획: `Covering index range scan on u using uq_universities_name_region` → `Covering index lookup on d using uq_departments_university_name` → `Single-row covering index lookup on b using uq_booth_department`. 세 단계 모두 인덱스만으로 끝나는 커버링 인덱스(조회에 필요한 컬럼이 인덱스에 다 있어서 테이블 본체를 읽지 않는 방식) 접근이다.
  ② Hot 부스의 80 ms는 order_items 25,575행에서 행마다 `orders` PK를 찾아가 상태를 확인하는 비용이다. 이것을 줄일 후보가 **`order_items(booth_menu_id, order_id, quantity, total_order_item_price)` 커버링 인덱스**다. **효과는 아직 재지 않았다** — 승인되면 LLD 단계에서 Flyway로 넣기 전에 실측하고, 개선이 확인될 때만 추가한다.

### 옵션 3: 혼합 — 인기 메뉴는 옵션 2, 매출 검색은 옵션 1

- **설명**: 인기 메뉴 API는 부스 우선 키셋으로 바꾼다(부스 안 순위라 계약이 깨지지 않는다). 매출 검색은 **매출순 정렬과 전체 기준 `rank`를 지키기 위해** 옵션 1(전체 집계 + `rank` 커서)로 둔다.
- **장점**: 두 API 모두 **응답 필드의 의미가 그대로**다. 인기 메뉴는 옵션 2의 이득을 전부 얻는다.
- **단점**: 매출 검색은 페이지마다 전체 집계(5만 기준 약 330 ms)를 계속 한다. 주문이 늘면 같이 느려지므로, 이 비용을 없애려면 **다음 단계(캐싱 또는 집계 테이블)로 넘겨야 한다** (policy 7.1의 ② 캐싱).
- **실측**: 인기 메뉴는 옵션 2와 같다. 매출 검색은 옵션 1과 같다.

> **검토했지만 제외한 변형**: 매출 검색에서 "검색에 걸린 부스만 매출순으로 집계"하는 방식도 재 봤다. `한`(부스 1,345개)에서 **244 ms**, `서경대학교`에서 86 ms로, 전체 집계(331 ms)보다 크게 낫지 않다. 걸린 부스 중에 Hot 학교(한성대)가 있으면 그 주문을 전부 읽어야 하기 때문이다. 또 `rank`가 "검색 결과 안 순위"로 바뀌므로 계약 변경도 옵션 2와 같다. 따라서 옵션에서 뺐다.

| 계약 변경 | 검색 의미 + 응답 형태 | 위 + **매출 검색 정렬·`rank` 의미 변경** | 검색 의미 + 응답 형태 |
| 이름 검색 인덱스 추가 | 불필요 | 불필요 | 불필요 |
| 쓰기 경로 영향 | 없음 | 커버링 인덱스를 넣으면 `order_items` INSERT마다 인덱스 1개 추가 갱신 | 옵션 2와 같음 |
| 구현 복잡도 | 낮음 | 중간 (쿼리 2단계) | 중간 |

## 결정 (Decision)

**확정**: **옵션 1** (개발자 승인 2026-11-10) — 기존 쿼리 구조와 응답 필드의 의미(전체 부스 기준 `rank`, 매출순 정렬)를 유지하고, 접두 일치 + 키셋 커서만 적용한다.

- 권고와 다르게 정한 이유: 개발자 선택. 요구사항(우측 와일드카드 + 필요 시 인덱스 + 커서 페이징)을 가장 작은 변경으로 충족하며 계약 변경이 검색 의미·응답 형태로 한정된다.
- **감수하는 것**: 완료 주문 전체 집계(5만 기준 160~330 ms)가 페이지마다 남는다. 주문이 늘어날 때의 대응(부스 우선 집계·캐싱)은 후속 이슈로 넘긴다.

<details>
<summary>이력 — 에이전트 권고안 (채택되지 않음)</summary>

**권고안**: **옵션 2** — 주문이 500만 건까지 늘어나는 계획에서, 주문 수에 비례하는 전체 집계를 두 API 모두에서 없애는 유일한 옵션이다.

- 매출 검색에서 잃는 것은 "전체 부스 기준 순위"와 "매출순 정렬"이다. 하지만 이 API는 이름으로 **특정 부스를 찾는** 화면이라 이름순이 자연스럽다고 판단했다. 전체 매출 순위는 `GET /api/statistics/booths/top`(TOP 10)이 계속 제공한다.
- 이 판단이 화면 요구와 맞지 않으면(검색 결과에 전체 순위가 꼭 필요하면) **옵션 3**이 차선이다. 그 경우 매출 검색의 집계 비용은 후속 캐싱 이슈로 넘긴다.
</details>

### 구현 규칙 (옵션 1)

- 검색어는 지금처럼 앞뒤 공백을 지우고 `%`·`_`·`!`를 이스케이프한 뒤 **`LIKE CONCAT(:keyword, '%') ESCAPE '!'`** 로만 비교한다. 앞쪽 와일드카드를 다시 붙이지 않는다.
- 응답은 `CursorPageResponse`, 커서는 `CursorCodec`으로 인코딩한 불투명 문자열이다. 요청 파라미터 이름은 OrderController와 같이 `encodedCursor`, `size`(기본 20)를 쓴다.
- **매출 검색**: 정렬은 지금과 같이 전체 부스 기준 `salesRank` 오름차순이다. `salesRank`는 `ROW_NUMBER`라 유일하므로 커서는 `(lastRank)` 하나로 충분하다.
- **인기 메뉴**: 정렬은 지금과 같이 `(학교명, 학과명, 부스 id, 부스 안 순위)`다. 페이지 단위는 **메뉴 행**이고 커서는 이 네 값이다. `(부스 id, 부스 안 순위)`가 유일하므로 tie-breaker(정렬 값이 같은 행끼리 순서를 하나로 정해 주는 값)가 된다 (policy 5.5). 학교명은 지역이 다르면 같을 수 있어(UNIQUE가 `(name, region)`) 학교명·학과명만으로는 유일하지 않다.
- 순위는 윈도 함수 결과이므로 커서 조건은 순위를 매긴 결과를 감싼 바깥 쿼리에 건다. 순위 계산 범위(전체 부스 / 부스 안)는 바꾸지 않는다.
- 인덱스는 추가하지 않는다.
- 응답 형태 변경은 `docs/api-spec/statistics.md`를 LLD보다 먼저 고친다.

## 결과 (Consequences)

### 개선 실측치

승인 후 구현을 마치고 **컨텍스트와 같은 조건**(5만 적재, 같은 검색어, Nginx `:8888`, 워밍업 5회 후 30회)으로 다시 재서 채운다.

| 항목 | Before | After |
|---|---|---|
| 매출 검색 `대학` p95 / 응답 행 | 776 ms / 14,009행 | |
| 매출 검색 `서경대학교` p95 | 285 ms | |
| 인기 메뉴 `대학` p95 / 응답 행 | 3,627 ms / 140,022행 | |
| 인기 메뉴 `서경대학교` p95 | 255 ms | |
| `EXPLAIN` 요약 | `booth` 14,093행 전체 조인 후 학교명 필터, 완료 주문 전체 집계 | |
| 집계 스캔 행 수 | order_items 101,138행 (검색어와 무관) | |

### 긍정적

- 응답 크기에 상한(`size`)이 생긴다. `대학`처럼 넓은 검색어로 14만 행을 내려보내는 일이 없어진다.
- 이름 조건이 기존 UNIQUE 인덱스의 range 스캔으로 처리된다. 인덱스를 추가하지 않으므로 쓰기 비용이 늘지 않는다.
- (옵션 2) 집계 비용이 전체 주문 수가 아니라 페이지에 든 부스의 주문 수에만 비례한다.

### 부정적 / 트레이드오프

- **검색 의미가 바뀐다.** `경영`으로 `서경대학교`를 찾을 수 없다. 반드시 학교명 **앞부분**부터 입력해야 한다.
- **응답 형태가 바뀐다** (`List` → `CursorPageResponse`). 프런트 수정이 필요하다.
- (옵션 2) 매출 검색이 매출순이 아니라 이름순이 되고, `rank` 필드를 낼 수 없다.
- (옵션 2) Hot 부스가 페이지에 들어오면 여전히 그 부스들의 주문을 전부 읽는다(5만 기준 80 ms). 커버링 인덱스로도 부족하면 부스별 매출 집계를 미리 계산해 두는 방식(캐싱·집계 테이블)이 다음 단계다.

### 후속 작업

- [ ] `docs/api-spec/statistics.md` 5·6번 갱신 (접두 일치, `encodedCursor`·`size` 파라미터, `CursorPageResponse` 응답)
- [ ] LLD 작성 — 두 단계 쿼리, 커서 레코드, 커버링 인덱스 실측 계획
- [ ] (커버링 인덱스를 넣는다면) `V21__*.sql` + `docs/erd/` 갱신 + 주문 생성 쓰기 영향 측정
- [ ] 같은 조건으로 After 측정 후 이 ADR의 "개선 실측치" 표 채우기
- [ ] (옵션 3을 고르는 경우) 매출 검색 집계 캐싱 이슈 분리

## 준수 확인 (Compliance)

- 커서 테스트: 같은 학교명(지역만 다름)이 여러 개일 때 페이지 경계에서 누락·중복이 없는지 통합 테스트(Testcontainers MySQL)로 확인한다.
- 접두 일치 테스트: 이름 중간에 들어 있는 검색어로는 결과가 나오지 않는지 확인한다.
- 실행 계획은 옵티마이저가 데이터 분포에 따라 바꾸므로(소량 테스트 데이터와 5만 적재 데이터의 계획이 다르다) 테스트로 고정하지 않는다. 대신 성능 측정 스크립트 `scripts/perf/statistics_search_bench.py`로 같은 조건을 재현한다 (policy 18.4).
- 리뷰 체크: 두 API 쿼리에 `CONCAT('%', …` 형태(앞쪽 와일드카드)가 다시 들어오지 않았는가.

### 에이전트 → 개발자 확인 요청

1. **작성 완료 보고** — ADR-0005, 이 파일
2. **옵션 요약** — 위 "비교 요약" 표
3. **권고안과 근거** — 옵션 2 (주문 수에 비례하는 전체 집계를 두 API 모두에서 없애는 유일한 옵션). 차선은 옵션 3
4. **열린 질문**
   1. 매출 검색 결과에 **전체 부스 기준 순위(`rank`)와 매출순 정렬**이 꼭 필요한가? 필요하면 옵션 3, 아니면 옵션 2
   2. `size`의 기본값과 상한 — 주문 목록 API처럼 기본 20으로 할지, 상한(예: 100)을 둘지
   3. 인기 메뉴의 페이지 단위를 "부스"(부스마다 메뉴 전부)로 해도 되는가? 메뉴 행 단위로 자르면 한 부스의 메뉴가 두 페이지에 걸칠 수 있다
   4. 학교명 검색 의미를 접두 일치로 바꾸는 것(예: `경영`으로 `서경대학교`를 못 찾음)에 프런트 합의가 되어 있는가
