## 컨텍스트 (Context)

### 요구사항 (사용자 지시 원문)

> "내용 전격 수정이 필요해. 서강대학교가 아니라 전체 대학교에 대해서 각 학과마다 하나씩 부스가 필요한 거야. docker exec -it mysql로 확인해보면 359개 대학이 있고, 학과는 14095개가 있어. 그러니 부스도 '서강'이 아니라 '서경'대학교를 제외한 14000개 이상의 부스 데이터 적재가 필요하며 메뉴는 14만개 정도가 필요하겠지? flyway로 넣는 방식이 부적합하면 말해줘(메뉴는 양이 좀 많긴함) 내용 다시 파악하고 전격 수정해."

컬럼별 값은 첫 지시를 그대로 따른다 (부스: `thumbnail_url`·`location`·`booth_numbers` NULL, `order_enabled` 1, 예금주·계좌·은행은 임의값, `booth_status` OPEN / 메뉴: 부스당 10개 = MAIN 5·SIDE 3·DRINK 2, 먹거리, 한·영·중 이름, `time_type` ALL, `is_sold_out` 0, 설명 NULL / `booth_operation`은 제외). 원문은 LLD에 인용한다.

### 이 결정이 필요한 이유

이전 요구(서강대 64개 부스·640개 메뉴)는 V15·V16처럼 Flyway 버전 마이그레이션(앱이 뜰 때 `db/migration`의 `V{N}__*.sql`을 번호 순으로 한 번씩 실행하고 `flyway_schema_history`에 기록하는 방식)으로 만들었다. 규모가 220배로 커지면서 두 가지가 달라졌다.

1. **양** — policy 3.3이 ADR로 정하라고 한 "대량 삽입 방식·트랜잭션 크기·인덱스 해제 여부"에 해당하는 규모가 되었다.
2. **성격** — V15·V16은 *실제* 대학·학과 목록(기준 데이터)이었다. 이번 부스·메뉴는 **예금주·계좌번호가 임의로 만든 더미 데이터**다. Flyway에 넣은 데이터는 그 앱이 뜨는 **모든 환경**에 들어간다.

> 이미 config 저장소에 올라갔던 서강대 한정 V17/V18은 어느 DB에도 적용되기 전에 되돌렸다 (config `011b43b`, 로컬 `flyway_schema_history` 최신 버전 16).

### 측정된 현상

프로토타입 SQL(아래 옵션 1·2에 공통인 집합 기반 `INSERT ... SELECT`)을 로컬 DB에서 `START TRANSACTION → 실행 → ROLLBACK`으로 재었다. 데이터는 되돌렸다 (롤백 후 booth 31 / booth_menu 242 확인).

| 항목 | 값 |
|---|---|
| 대상 | `booth`, `booth_menu` INSERT |
| 데이터 규모 | 대학 359 / 학과 14,095 (서경대 33) → **부스 14,062 / 메뉴 140,620** |
| 데이터 분포 | 서경대학교 제외 학과당 부스 1 (`UNIQUE(department_id)`), 부스당 메뉴 10 = MAIN 5·SIDE 3·DRINK 2 (사용자 지정) |
| 측정 조건 | 로컬 Docker MySQL 8.0.46 (`festival2`), 앱 3대 기동 중, 인덱스·FK 켠 상태, 1회 측정 |
| 부스 14,062건 INSERT | **0.48초** (한 문장) |
| 메뉴 140,620건 INSERT | **2.41초** (한 문장) |
| 트랜잭션 전체 | 변경 행 154,682 / **잠긴 행 70,894** / ROLLBACK 1.08초 |
| 결과 검증 | 14,062개 부스 전부 (메뉴 10, MAIN 5, SIDE 3, DRINK 2, 부스 안 중복 메뉴명 0) |
| 비교 기준 | Testcontainers에서 V1~V16(학과 14,062행 포함) 전체 적용 ≈ 2.8초 |

해석:

- **속도는 어느 방식이든 문제가 아니다.** 한 문장으로 3초 안에 끝난다 → 적재 중 인덱스·FK를 끌 이유가 없다.
- **잠금은 신경 써야 한다.** `INSERT ... SELECT`는 원본 행(`booth`·`departments`)에 공유 잠금(다른 트랜잭션이 그 행을 수정하지 못하게 거는 읽기 잠금)을 건다. 앱의 `BoothScheduler.updateBoothStatusEveryMinute`가 **매분 3대에서** `booth`를 UPDATE하므로, 한 문장으로 넣으면 그동안 스케줄러가 기다린다. 나눠 넣으면 한 번에 붙잡는 시간이 짧아진다.
- 따라서 결정의 핵심은 속도가 아니라 **"이 더미 데이터를 어떤 경로로, 어느 환경에 넣는가"** 다.

## 결정 동인 (Decision Drivers)

1. **더미 데이터가 원치 않는 환경에 들어가지 않을 것** — 특히 `cd-prod.yml`(main push → 서브모듈 포함 빌드·배포) 경로. 주문 가능(`order_enabled = 1`)·영업중(`OPEN`) 부스에 **임의로 만든 계좌번호**가 붙는다. 우연히 실존 계좌와 겹칠 수 있고, 실사용 환경이라면 사용자가 그 계좌로 송금할 수 있다
2. **되돌릴 수 있을 것** — 성능 실험용 데이터는 지우고 다시 넣는 일이 잦다 (#6의 다음 단계: 수백만~수천만 건 주문)
3. **#6의 다음 단계와 같은 도구를 쓸 것** — 주문 수백만 건은 Flyway로 넣을 수 없다. 부스·메뉴만 다른 경로로 넣으면 적재 방식이 둘로 갈린다
4. 팀원 로컬에 재현하는 수고 (자동 vs 명령 한 줄)
5. 테스트·CI 시간 (Testcontainers는 테스트 실행마다 모든 마이그레이션을 빈 DB에 적용한다)

## 고려한 옵션 (Considered Options)

### 옵션 1: Flyway 버전 마이그레이션 (`V17` 부스, `V18` 메뉴) — **채택**

- 설명: 지금까지와 같다. `db/migration`에 집합 기반 `INSERT ... SELECT`(행을 한 건씩 보내지 않고, 학과 목록을 SELECT한 결과 전체를 한 문장으로 INSERT하는 방식) 두 파일을 추가한다.
- 장점:
  - 앱만 띄우면 모든 로컬 DB에 자동으로 들어간다. 별도 절차 없음
  - `flyway_schema_history`에 "언제 들어갔는지"가 남는다
- 단점:
  - **dev·prod·Testcontainers 등 앱이 뜨는 모든 환경에 더미 부스 14,062개와 가짜 계좌가 들어간다.** 환경별로 막을 방법이 없다
  - **되돌리기 어렵다.** 적용된 파일은 수정 금지(policy 4.1)라, 지우려면 `DELETE` 마이그레이션을 또 추가해야 한다. 그 사이 붙은 주문(#6)까지 FK로 얽힌다
  - policy 3.3 "적재 스크립트는 `src/main`에 두지 않는다"와 어긋난다 (`db/migration`은 `src/main/resources` 아래)
  - Flyway는 파일 하나를 한 번에 실행하므로 나눠 넣어도 파일 단위 재개만 가능하다
  - 모든 통합 테스트 실행에 약 3초·15만 행이 더해진다 (V1~V16 ≈ 2.8초 → 대략 2배)
- 실측 효과: 적재 자체는 2.9초 (위 표)

### 옵션 2: `scripts/seed/`의 SQL 스크립트를 필요한 DB에만 수동 실행 — 에이전트 권고안 (미채택)

- 설명: 옵션 1과 같은 SQL을 **운영 코드 밖** `scripts/seed/`에 두고, 넣고 싶은 DB에서만 실행한다.
  ```bash
  docker exec -i mysql mysql -uroot -p1234 festival2 < scripts/seed/01_booths.sql
  docker exec -i mysql mysql -uroot -p1234 festival2 < scripts/seed/02_booth_menus.sql
  ```
  - 부스: 한 문장 (0.48초)
  - 메뉴: 부스 순번 기준 **2,000개 부스(= 메뉴 20,000건)씩 8문장**으로 나눈다. 각 문장은 자동 커밋(문장 하나가 끝나면 바로 확정)이라 잠금을 붙잡는 시간이 문장당 약 0.35초(실측 2.41초 ÷ 7, 추정)로 줄어든다
  - **멱등하게 쓴다**(여러 번 실행해도 결과가 같게) — 이미 부스가 있는 학과, 이미 메뉴가 있는 부스는 건너뛴다. 중간에 실패하면 **같은 파일을 다시 실행하면 이어서** 들어간다
  - 되돌리기용 `99_reset.sql`(서경대 외 메뉴 → 부스 순으로 삭제)을 함께 둔다
- 장점:
  - **넣을 환경을 사람이 고른다.** prod·dev·Testcontainers에는 들어가지 않는다
  - 지우고 다시 넣기가 자유롭다 → #6에서 규모를 올려 가며 측정할 때 그대로 쓴다
  - policy 3.3(위치·트랜잭션 분할·재개 전략)을 그대로 만족한다. #6의 주문 적재도 같은 폴더·같은 방식으로 이어진다
  - 테스트·CI 시간에 영향 없음
- 단점:
  - **자동이 아니다.** 팀원마다 로컬 DB에 명령 두 줄을 직접 실행해야 한다 (README·LLD에 명시)
  - 어느 DB에 들어갔는지 Flyway가 기록해 주지 않는다 → 실행 결과(건수·소요 시간)를 이슈에 남기는 규칙으로 대신한다 (policy 3.3)
  - Flyway 마이그레이션보다 **나중에** 실행해야 한다 (V16까지 적용된 DB 전제). 순서를 어기면 대상 학과가 없어 0건이 들어간다 → 스크립트 끝에 건수 검증 SELECT를 둔다
- 실측 효과: 부스 0.48초 / 메뉴 합계 약 2.4초 (8문장 분할은 추정치, 구현 후 실측해 결과 절에 기록)

### 옵션 3: Flyway를 쓰되 더미 전용 위치(`db/seed`)를 로컬 프로필에서만 켠다

- 설명: `db/seed/R__seed_booths_and_menus.sql` 같은 반복 마이그레이션(버전 번호 없이, 파일 내용이 바뀔 때마다 다시 실행되는 Flyway 파일)을 두고, `spring.flyway.locations`에 `classpath:db/seed`를 **local 프로필에서만** 추가한다.
- 장점:
  - 로컬은 자동, prod·dev에는 들어가지 않는다 (옵션 1·2의 장점을 반씩)
- 단점:
  - `application-*.yml`(config 서브모듈)을 바꿔야 한다. 이 저장소 규칙상 에이전트가 설정 파일을 직접 열지 않으므로 개발자 작업이 필요하다
  - 반복 마이그레이션은 **파일이 바뀌면 전체를 다시 실행**한다 → 매번 "지우고 다시 넣기"가 되는데, #6에서 주문이 이 메뉴를 참조하기 시작하면 FK 때문에 지울 수 없다. 버전 마이그레이션(`V`)으로 두면 번호가 `db/migration`과 한 줄로 섞여, 로컬에만 있는 버전 때문에 이후 스키마 마이그레이션이 순서 검증에 걸린다(`outOfOrder` 설정 필요)
  - 파일 하나 = 트랜잭션 하나라 나눠 넣기·재개가 옵션 2보다 불편하다
  - Testcontainers 프로필에 켤지 말지를 또 정해야 한다
- 실측 효과: 적재 시간은 옵션 1과 같다

## 결정 (Decision)

**확정**: 옵션 1 (개발자 승인 2026-09-17) — 결정 동인 1(운영 환경 유입)이 성립하지 않는다. 개발자 답변: *"실제 운영에 쓰일 프로젝트가 아니라서 상관없어."* 남는 기준은 팀원 로컬 재현(자동)이며, 이 기준에서 옵션 1이 가장 낫다.

**권고안 이력**: 옵션 2 — 가짜 계좌가 붙은 주문 가능 부스가 앱이 뜨는 모든 환경에 따라가는 것을 막고(동인 1), 지우고 다시 넣기 쉬우며(2), #6의 주문 적재와 같은 경로라는(3) 이유로 권고했다.

> **"Flyway로 넣는 방식이 부적합한가"에 대한 답 (작성 당시)**: 양(14만 건) 때문에 불가능하지는 않다 — 실측 2.9초다. 부적합할 수 있는 이유는 **양이 아니라 성격**(모든 환경에 가는 더미)이었고, 운영 환경이 없다는 답으로 그 이유가 사라졌다.

### 구현 규칙

- 파일: 테이블별로 나눈다 — `V17__insert_booths.sql` → `V18__insert_booth_translations.sql` → `V19__insert_booth_menus.sql`. Flyway는 파일 하나를 한 트랜잭션으로 실행하므로, **파일을 나눠 트랜잭션을 테이블 단위로 끊는다** (policy 3.3 "전부 한 트랜잭션 금지"를 이 단위로 지킨다. 가장 큰 메뉴 파일도 실측 2.4초)
- 대상: `NOT (universities.name = '서경대학교' AND region = 'SEOUL')`인 학과 전체. `university_id`를 숫자로 박지 않는다 (V16 관례)
- 방식: 집합 기반 `INSERT ... SELECT` 한 문장. 저장 프로시저는 쓰지 않는다
- 결정적 생성: `RAND()`를 쓰지 않는다. 임의값(예금주·은행·계좌·번역 문구·메뉴 배정)은 `(대학명, region, 학과명)` 정렬 순번(`ROW_NUMBER()`)의 함수로 만든다 → 같은 대학·학과 데이터면 어느 환경에서든 같은 결과
- 인덱스·FK: **끄지 않는다** (켠 상태 실측 2.9초)
- 메뉴: 메뉴명 종류를 늘린다 — 기존 데이터와 무관하게 짓는다 (개발자 지시)
- 번역: 부스당 KO·EN·ZH 3행. 부스명·설명은 **짧게, 비슷한 문구 반복 허용** (개발자 지시)
- `booth_status`는 `OPEN`으로 넣는다. 01:00 스케줄러가 CLOSED로 바꾸는 것은 감수한다 (개발자 지시)
- 매니저 계정은 이번 범위에서 제외한다 (다음 작업)
- 검증: 로컬 DB에서 트랜잭션 롤백으로 건수·분포를 확인하고, `./gradlew test`로 빈 DB에 V1~V19 적용을 확인한다. 결과는 이슈 #12에 기록한다

### 긍정적

- 앱을 띄우기만 하면 모든 로컬 DB에 같은 부스·번역·메뉴가 들어간다 (팀원 재현 비용 0)

### 부정적 / 트레이드오프

- dev·prod·Testcontainers 등 앱이 뜨는 모든 환경에 더미가 들어간다 (운영 환경이 없어 수용)

- 모든 통합 테스트 실행의 마이그레이션 시간이 늘어난다 (실측 2.8초 → 4.1초)

### 에이전트 → 개발자 확인 요청

1. **작성 완료 보고** — ADR-0002 `docs/adr/ADR-0002-booth-menu-bulk-seed-path.md`
2. **옵션 요약** — 위 "비교 요약" 표
3. **권고안과 근거** — 옵션 2. 개발자가 그대로 따를 필요는 없다
4. **판단이 필요한 열린 질문**

   1. **옵션 선택** — 1(Flyway) / 2(`scripts/seed`, 권고) / 3(Flyway 로컬 전용) → ✅ 옵션 1
   2. **메뉴 다양성** — 프로토타입은 먹거리 후보 47개(MAIN 23·SIDE 13·DRINK 11)를 돌려 쓴다. 14만 건이면 메뉴명 하나가 약 3,000번 반복된다. 이대로 괜찮은가, 아니면 후보를 늘릴까 (예: 메뉴명 검색·번역 사전(`booth_menu_dictionary`) 성능을 잴 계획이 있다면 종류가 더 필요하다)
   3. **`booth_translation`** — 부스 목록·검색 API 3종(`BoothRepository.findBoothsByLanguage` 등)이 `JOIN BoothTranslation`(내부 조인)이라, 번역 행이 없는 신규 부스 14,062개는 **목록 API에 하나도 나오지 않는다.** 부스 목록 성능을 잴 거라면 번역(부스당 KO·EN·ZH 3행 = 42,186행)도 함께 넣어야 한다. 넣는다면 영·중 학과명은 무엇으로 채울까 (예: 한국어 학과명 그대로)
   4. **`booth_status = OPEN` 유지** — `BoothScheduler.dailyBoothStatusToClose`가 **매일 01:00에 모든 부스를 CLOSED로** 바꾼다. 앱이 켜진 채 하루가 지나면 적재한 OPEN이 사라진다. 그대로 둘까, 필요할 때 다시 OPEN으로 바꾸는 스크립트를 함께 둘까
   5. **매니저 계정** — 신규 부스를 운영할 `managers` 행이 없다. 부스 관리자 API(주문 조회 등) 성능을 잴 계획이면 필요하다. 이번에 함께 넣을까, #6 주문 단계에서 넣을까
