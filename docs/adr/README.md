# ADR (Architecture Decision Records)

중요한 아키텍처/기술 의사결정과 그 근거를 기록한다. **결정 자체보다 "왜 그렇게 정했는가"와 "무엇을 포기했는가"가 이 문서의 본체**다.

이 프로젝트의 결정은 대부분 **성능이 걸린 결정**이다. 따라서 여기의 ADR은
`docs/templates/adr.md`가 요구하는 **실측 수치(Before/After)** 없이는 "승인됨" 상태가 될 수 없다.

새 ADR은 [`../templates/adr.md`](../templates/adr.md)를 복사해 `ADR-NNNN-<kebab-slug>.md`로 만든다. 번호는 기존 최대 번호 + 1 (4자리).

> **작성 후 아래 표에 반드시 한 줄을 추가한다.** (AGENTS.md 워크플로 ②)
> 상태가 바뀌면(대체됨·폐기됨) 표의 상태 칸도 함께 고친다. **인덱스가 없는 ADR은 없는 것과 같다.**

## ⛔ ADR 작성 후에는 반드시 멈춘다 (AGENTS.md ②-1)

**에이전트는 ADR을 다 쓰면 거기서 작업을 멈추고 개발자의 확인을 받는다.**
아키텍처 결정은 개발자가 내리는 것이고, 에이전트는 선택지를 정리해 제시하는 역할이다.

| | 내용 |
|---|---|
| **전달할 것** | ① 작성 완료 보고 ② 옵션 요약(얻는 것/포기하는 것) ③ 권고안과 근거 ④ 판단이 필요한 열린 질문 |
| **하지 않을 것** | LLD 작성, 구현·마이그레이션 작성, 커밋·동기화·PR, **상태를 스스로 "승인됨"으로 바꾸기** |
| **응답 후** | ADR의 "개발자 응답 기록" 표를 채우고(**추가 지시는 원문 그대로**), 상태·승인 칸·"확정" 줄을 갱신한 뒤 ③으로 |

- 개발자가 **권고와 다른 옵션**을 고를 수 있다. 그때는 "결정" 절을 그 옵션으로 고쳐 쓰고 권고안은 이력으로 남긴다.
- 개발자 지시가 ADR의 전제를 뒤집으면 **ADR을 고쳐 다시 확인을 요청**한다.
- 아래 목록에 **"제안됨" 상태로 남아 있는 ADR은 아직 구현 근거가 아니다.**

## 고려한 옵션은 2~3개

- **2개** — 선택지가 명확히 둘로 갈릴 때
- **3개** — 절충안·단계적 도입안(예: ① 현상 유지 ② 인덱스만 추가 ③ 스키마 비정규화)이 **실제로 성립할 때만**
- 4개 이상으로 늘리지 않는다. 개발자가 고르기 어려워지고 비교의 초점이 흐려진다.
- **검토하지 않은 허수 옵션을 채우지 않는다.** 2개로 충분하면 2개만 쓴다. "아무것도 하지 않기"도 정당한 옵션이다.

## ADR이 필요한 결정 (AGENTS.md ②)

아래에 해당하면 **구현 전에 반드시** ADR을 쓴다.

| 유형 | 예 |
|---|---|
| 스키마 개편 | 대학-부스 연관관계 도입, `orders.booth_id` 비정규화, `Department` enum의 테이블 승격 |
| 대량 데이터 삽입 방식 | 배치 insert vs 저장 프로시저, 트랜잭션 크기, 적재 중 인덱스/FK 해제 여부 |
| 성능 개선 기법 선택 | 인덱스 전략, 캐싱 전략(키·TTL·무효화), 페이징 전략 변경 |
| 저장소·구조 변경 | Read Replica 도입, CQRS 적용, MongoDB 등 신규 저장소 도입 |
| 계약 변경 | `BaseResponse` 스키마 변경(에러 코드 필드 추가 등), SSE 이벤트 이름 체계 변경 |
| 방침 변경 | `docs/policy/development-policy.md`의 어떤 절이든 바꿀 때 (policy 18장) |

기존 결정 범위 안의 단순 작업이면 ADR을 생략할 수 있으나, **이슈에 생략 사유를 남긴다.**

## 상태의 의미

| 상태 | 뜻 |
|---|---|
| 제안됨 | **개발자 확인 대기 중.** 작성은 끝났지만 아직 구현 근거로 쓸 수 없다 (②-1) |
| 승인됨 | **개발자가 옵션을 선택한, 현재 유효한 결정.** 모든 LLD·구현이 이를 전제한다 |
| 대체됨 (→ ADR-NNNN) | 후속 ADR이 뒤집었다. 본문은 **결정 이력으로 보존**하며 고쳐 쓰지 않는다 |
| 폐기됨 | 결정 자체가 무효화되었고 대체 결정도 없다 |

## 작성 시 자주 놓치는 것

- **ADR을 쓰자마자 LLD·구현으로 넘어가는 것** — ②-1에서 반드시 멈춘다. 가장 자주 어기는 규칙이다
- **개발자에게 "옵션 요약"과 "열린 질문" 없이 결론만 통보하는 것** — 개발자가 고를 수 없으면 게이트의 의미가 없다
- **개발자 추가 지시를 요약해서 기록하는 것** — "개발자 응답 기록"에는 **원문 그대로** 남긴다
- **컨텍스트의 "측정된 현상" 표를 비워 두는 것** — 데이터 규모·분포·`EXPLAIN`·p95가 없으면 성능 ADR로 성립하지 않는다
- **결과의 "개선 실측치"를 컨텍스트와 다른 조건에서 잰 것** — 조건이 다르면 Before/After 비교가 무의미하다
- 옵션을 형식적으로 2개만 채우고 실제로는 하나만 검토한 것 — **검토하지 않은 허수 옵션을 적지 않는다**
- **트레이드오프를 비워 두는 것** — 이 프로젝트의 결정은 대부분 무언가를 포기한다(쓰기 지연, 저장 공간, 최종적 일관성). 숨기지 않는다
- 스키마를 바꾸는 ADR인데 **ERD 갱신·기존 데이터 백필 계획을 후속 작업에 안 적는 것**
